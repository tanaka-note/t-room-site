# 家計簿

公開先 `/household/`、Worker `t-room-household`、専用D1 `household-db`。機能要件は[設計書](../docs/household-design.md)を参照する。

## Cloudflareに内容を渡さない端末側暗号化

通常運用は `ENCRYPTION_REQUIRED=true`。家計ごとのランダム32バイト鍵からHKDFでAES-GCM-256鍵とHMAC識別子鍵を分離する。口座名・内訳・基準日付き残高履歴・明細・分類・過去チャートを端末内で暗号化する。記録種別・不透明なID・家計の所属・revision・更新時刻・件数・サイズ・通信元はサーバーから見える。AADはサービス専用文字列・家計ID・鍵ID・種別・不透明IDを結び付け、IVは保存ごとに乱数12バイトを生成する。家計の内容、PRF出力、生の家計鍵・秘密鍵をWorker・監査・ログへ渡さない。配信コードと端末は信頼境界に含む。

既存パスキーで通常ログインすると、同じcredentialのT-Cloud用暗号化済みRSA秘密鍵を端末内で解除・再利用する。既存のHousehold用鍵があれば優先し、どちらもなければPRF/HKDFで包んだRSA-OAEP-3072鍵を端末内で自動生成する。Security Centerでの別の利用準備・家計鍵承認は不要。所有者の最初のログインで家計鍵・復旧用envelope・本人と準備済みの共有先への委譲を一括確定し、そのまま既存データを暗号化する。同時ログインは既存の鍵へ収束し、登録済みの鍵を置き換えない。

委譲先はSecurityとHouseholdが現在有効と確認した、同じ家計の承認済みIdentity・credential・連携だけ。所有者の通常ログイン、再読込や更新時に不足する委譲を自動作成する（通常の再確認は60秒間隔、更新ボタンでは即時）。既存の暗号化済み利用者鍵を持たない閲覧者は、最初のログインで自分の鍵を自動準備した後、所有者の次の通常利用を待ち、再ログインする。`owner`と`viewer`は同じ家計鍵を使い、千晴の家計は独立する。認証・role・失効を維持し、鍵だけで編集権限を与えない。パスキーの新規・追加登録には従来どおり第一管理者の招待・承認が必要。PRF非対応・鍵不足では平文へfallbackしない。Security Centerの鍵管理は復旧用として残し、旧 `#household-setup` リンクは家計簿へ移動する。

検索・収支集計に加えて、資産推移計算、内容検証、CSV生成、旧JSON読込を端末で実行する。通常保存は変更された記録だけを暗号化する。暗号文・revisionのCAS・操作IDは同じD1 batchで確定し、再送では生成済みの同じ暗号文を使う。サーバーは認可・暗号化envelopeの形式・件数・サイズを検証し、内容の意味や参照整合性は端末で検証する。家計本文10MiBの上限は維持し、暗号化後は24MiB、API本文26MiB、暗号化バックアップのファイル選択32MiBまでとする。

再読込時は、有効なサーバーsessionを先に照合し、そのsession ID・家計ID・鍵IDに固定したIndexedDB内の非抽出CryptoKeyを使う。生のPRF・家計鍵・秘密鍵のバイト列は端末保存しない。所有者では再読込後の自動委譲用に、同じsessionへ固定した非抽出RSA CryptoKeyも保存する。鍵cacheがない／壊れている場合はパスキーで再解除する。別sessionへ切り替える時・ログアウト・失効時は鍵と表示内容を消去し、遅延応答を破棄する。端末側cacheから認証の期限・権限を延長しない。

暗号化済みの家計の再読込は、認証済みsession応答に含む `encryptionMigrationRequired=false` を利用し、初期表示前のAPIをsession照合と暗号文取得の2回にする。判定はその家計の保持中の全世代をサーバーで確認し、旧形式の応答で判定がなければ従来の移行確認を行う。未移行世代がある所有者は全世代の暗号化・照合を完了してから表示する。鍵cacheの再利用時は同じ鍵を再保存しない。

不足する共有鍵の確認・委譲は画面を描画した後の別処理とし、表示を待たせない。通常の60秒間隔・同時処理のまとめ・更新ボタンの強制確認を維持する。ログアウトやsession切替では保留処理を取り消し、実行中の応答も世代番号で破棄する。共有確認で401/403が返れば通常のAPIと同様に表示と鍵を消去する。暗号文の全件取得・端末内復号は維持し、永続的な平文cacheやオフライン表示は追加しない。

### バックアップ

手動JSONは `troom-household` v3。暗号化済み記録・家計ID・鍵ID・T-Cloud管理者公開鍵で暗号化した復旧用家計鍵と、記録集合全体のSHA-256を含む暗号化manifestを保存する。個々の復号に加え、manifestで記録の欠落・重複・改変を検出する。CSVは利用者が明示して書き出す平文ファイル。v1/v2 JSONは端末内で検証し、現行家計の鍵で暗号化してから復元する。他家計・別鍵のv3は第一管理者の端末で復旧用鍵を解除し、復元先の鍵で再暗号化する。認証情報・role・連携・権限は手動バックアップから取り込まない。

`household_crypto_config`、`household_crypto_vaults`、`household_crypto_grants`を家計データと同じD1 snapshotに含める。再利用したT-Cloud用の暗号化済み秘密鍵も、その解除方式を示す情報と一緒に既存のHousehold vault行へ複製し、Security DBの別時点のsnapshotに家計鍵の正本を依存させない。schema・バックアップ形式は変更しない。定期保存は復号せず、日次30・月次12の既存運用を維持する。暗号化された復旧用鍵を開くには、既存T-Cloud管理者秘密鍵を解除できるパスキーまたは既存の管理者復旧手段が必要。これを失うとDB・手動JSONがあっても復号できない。旧DBバックアップ（0006、v2/v3）も元のschemaで隔離復元してから0007へ進める。復元で古いアカウント・credential・連携を自動有効化しない。

### 移行・公開手順

自動準備の修正PRはコードとローカルfixtureだけを変更する。本番の鍵準備、データ移行、旧バックアップ削除は行わない。

1. 合意した保守時間に0007を適用し、Backupのregistry/schema guardとそれをbundleするSecurity・Diaryを対応版へ揃える。通常のコード公開だけではmigrationは適用されない。HouseholdとSecurityは新しいService Binding RPC・公開暗号モジュールが両方必要で、片方だけの公開を利用開始扱いにしない。
2. 自動準備にはSecurityとHouseholdの両対応版が必要。Securityを先に公開し、Householdを公開する。既に0007適用済みなら追加migrationは不要。通常設定 `ENCRYPTION_REQUIRED=true` を維持する。
3. 各家計の所有者が既存パスキーで通常ログインし、鍵の自動準備に続けて移行する。端末で現在世代と保持中の全旧世代を順次取得・暗号化・復号照合し、非公開世代へ準備する。サーバーの暗号文読戻し・revision CASの成功時だけ元の平文世代を暗号化済み世代へ置き換える。家計の内容と旧世代の作成／利用日時を保持する。旧平文操作の再送hashは推測照合に使われないランダム値へ置き換え、操作ID・結果・時刻は保持する。失敗時は元世代を残して再開できる。処理中の旧復元リースがある場合は期限切れ後に再開する。閲覧者による移行は不可。
4. 両家計について `crypto_version=0` の世代が0件であること、定期保存の成功、隔離DBからの端末内復号と手動v3復元を確認する。通常利用はtrueで継続し、古いクライアントの平文更新を拒否する。実Android/iOSのPRF・再読込・失効・T-Cloud管理者復旧は模擬PRF試験とは別に確認する。
5. D1 Time Travel、以前の手動JSON、旧R2バックアップ、作業用exportに平文が残る。既存のv1/v2 DB世代は通常のv3世代整理対象外のため、期限経過だけで消えると判断しない。棚卸しし、復旧可能な暗号化コピーを検証してから別途承認した再暗号化／削除または保持期限終了を記録する。それまでは既存保存物も含めた移行完了と表示しない。この変更で過去のCloudflareの読取可能性を遡ってなくすことはできない。

移行後の切り戻しに旧平文クライアントを使わない。暗号化対応版と鍵envelopeを保持して修正し、原本を平文へ戻さない。`ENCRYPTION_REQUIRED=false`は既に暗号化準備済みの家計を平文運用に戻すスイッチではない。

Securityの `node --test test/household-automatic.test.js` は実Worker・合成データで自動委譲、権限、競合、鍵snapshot復元を検証する。`node test/household-automatic.browser.mjs` はChromiumの仮想認証器と本物のWebAuthn/PRF・署名検証で通常ログインから両家計の自動移行までを確認する。実機の認証器との互換性は別に確認する。

Householdの `node --test test/encryption.test.js test/key-management.test.js`、`node test/encryption.browser.mjs`、Backupの暗号化復元fixtureは合成データ・模擬PRFを使う。`node test/encryption-performance.mjs 20000`で上限規模の端末暗号化・差分保存・バックアップ検証を測定できる。実端末WebAuthnや本番復号の確認とは区別する。

## 初版

「インプット」からの収入・支出登録（全件集計対象）、月別／年別集計、分類・フリーワード検索、自由な口座と内訳、全登録口座の月末資産合計チャート、CSV出力、バックアップ保存・復元を提供する。予算管理とCSV・PDF・画像からの明細取り込みは含めない。

田中宏知の初期データだけに「減価償却」口座の内訳1件を0円で用意した。追加する独立家計には標準分類だけを用意し、口座・残高・明細・資産履歴は空で開始する。家計明細と口座残高は独立し、一方の操作で他方を増減しない。口座画面で基準日付きの残高を入力し、その履歴から資産推移を自動集計する。マイナス残高に対応する。

## 残高入力と資産推移

口座一覧は現在残高（内訳の合計）の大きい順に自動表示する。正の残高、0円、負の残高の順となり、同額の口座は取得時の順序を維持する。保存後・更新・再読込のたびに並べ直し、保存データや内訳の順序は変更しない。

口座の残高編集には「残高の基準日」を必須とし、日本時間の今日以前の日を指定する。各口座の`balances`へ日付と内訳を保存し、同じ日の保存は訂正、別の日は履歴追加とする。現在残高の`items`には最も新しい基準日の内訳を保持し、過去日の追加・訂正で現在値を巻き戻さない。保存済み履歴の選択と訂正は口座画面だけで行う。日付・内訳・残高は既存のrevision・冪等操作IDと同じ原子的な更新で確定する。

各月末以前の最新記録を口座ごとに選び、内訳合計を集計する。翌月の記録を前月へ使用しない。入力のない月は直前の記録を繰り越し、最初の記録より前を0円で補わない。基準日未入力の既存口座がある場合は、不完全な資産合計を表示しない。暗号化運用では端末で復号後に`assetHistory`を計算し、定期ジョブや手動の月末確定操作は使わない（旧互換APIだけはGET `/api/data`で計算済み値を返す）。当月は今日までの暫定値として表示し、採用元の基準日を記録一覧に表示する。

資産推移は編集者でも閲覧専用とし、月末記録の追加・編集・削除UIと`snapshot.*`・`historical.*`変更操作を廃止する。移行済み・保存済みの元記録はDBとバックアップに保持する。チャート・月末一覧の集計は、2026年9月までは保存済み値を優先し、2026年10月以降は基準日付き口座残高から計算した値を優先する（`ACCOUNT_ASSET_PRIORITY_MONTH`）。残高の訂正・口座追加・バックアップ復元でも同じ規則を使い、不完全な集計を旧取り込み値で隠さない。口座の対応付け機能は設けず、新しい対応付けは画面・APIで受け付けない。旧版バックアップ等に対応情報がある場合だけ、既存の表示と復元の互換性のため維持する。

2026年10月分のマネーフォワード取得値（10/30時点、`sourceAsOf`付き）は元記録として保持する。現在のチャートは登録口座の10月末以前の最新残高を採用し、取り込み値で固定しない。11月以降も各月末以前の最新記録を合算する。口座を保存した直後とデータ再取得時に再計算し、別途月末処理を待たない。基準日のある残高がない場合は推測の金額を作らない。

初期表示は全期間。My Investmentと同じく、1・3・6ヶ月／1・2・3・5・7・10年を記録期間に応じて表示する。最新の月末を終点に、指定月数前の月末も含む（毎月の記録があれば1ヶ月は2点、1年は13点）。表示対象は全登録口座の資産合計で固定し、口座選択は設けない。期間の変更は表示だけに反映し、金融データやrevisionを変更しない。

資産推移の開始は2022年6月30日。`0004` migrationはそれより前の月末記録と移行履歴を、非アクティブな復元世代も含めて物理削除する。対象がアクティブ世代にあればrevisionを進め、編集中の旧revisionによる上書きを拒否する。APIとDBの両方で開始月を制限し、古いバックアップからの復活も防ぐ。家計明細の日付・口座残高・分類は変更しない。本番適用時はTime Travelの復旧点、削除件数、保持対象のハッシュ一致を確認する。

チャートは表示された要素の実寸から描画し、非表示中の幅を使用しない。ResizeObserverと表示切り替えで再描画する。金額軸は円・万円・億円・兆円の適切な単位、年月軸は横幅に合わせた間隔とし、文字は12pxを維持する。全期間を含め、表示中の最小値・最大値の外側に変動幅の5%だけ余白を取る。目盛りの丸めで表示範囲を広げず、同額・1件の場合だけ残高の0.05%（最低1円）を上下へ取る。期間・口座・記録の変更で再計算し、ホバーでは軸を動かさない。精密な目盛りは桁を省略せず、必要な横幅を確保する。

マウスのホバーは金額・年月・グラフ上の点だけをプレビューし、確定月は動かさない。マウスが外れたら確定月へ戻す。クリック・タップ・指のドラッグと、チャートにフォーカスした左右キー・Home・Endで確定月を変更する。シークバーと前後ボタンは設けない。比較は選択月のNヶ月前（1・3・6ヶ月、1・2・3・5・7・10年）、全期間は表示開始月を基準にする。比較先の月が欠損している場合は比較先の記録なしと表示し、0円で補完しない。全月の丸印やTab移動先は作らず、選択点と単独の記録だけに印を付ける。欠損月や口座の未記録は線を切り、0円・日次値・推定前月比を生成しない。

記録一覧は年単位で折りたたみ、初回は最新年を開く。スマートフォンでは記録を縦に並べる。閲覧専用でも期間と確認する月を選べるが、編集・削除はできない。ログアウト時はチャートと選択値も消去する。旧口座との新しい対応付けは行わない。

## 入力と表示

内訳の削除は共通確認ダイアログを通し、キャンセル・Esc・戻るで元の入力を保持する。上下ボタンで安定した内訳IDのまま並び替え、選択した基準日の保存時に確定する。他の基準日や家計明細は変更しない。

金額は入力欄も3桁区切りにし、符号・整数円・範囲を検証して数値へ戻して保存する。現在の資産合計は画面幅を使う1列配置、スマホの収支カードと明細は余白を縮める。

新規・編集明細は収入／支出だけとし、口座・振替・計算対象チェックを設けない。保存時も口座参照なし・集計対象へ正規化する。既存の通常明細は計算対象外フラグによらず集計する。旧バックアップの振替は復元互換性のため保持し、過去の振替として集計から除外する。CSVの計算対象列も同じ基準とする。

分類別集計は収入・支出の2つの枠に分け、各枠に合計金額と大項目を表示する。大項目を押すと中項目ごとの金額をその場で開閉できる。各行の「収入／」「支出／」は省略する。大項目・内訳とも「その他」で始まる項目を末尾に置き、それぞれの中で合計金額の大きい順、同額は分類名の日本語順とする。条件に合う明細のある項目だけを表示する。月別・年別、分類・検索の絞り込みを内訳にも適用し、一覧の200件表示制限によらず条件に合う全件を集計する。再描画時は残っている大項目の開閉状態を保持し、ログアウトで消去する。閲覧専用でも内訳を開ける。

分類マークの色はユーザー提供のマネーフォワード MEの画面に合わせ、写っていない支出分類は[公式カテゴリ説明](https://support.me.moneyforward.com/hc/ja/articles/900004380703)の画像を参照する。内訳は大項目と同色を使い、収入は既存の緑とする。文字と金額は通常色を保ち、分類名と開閉マークを併記する。

明細一覧は初回表示・再読み込み・ログアウト時に支出を選択する。上部の「収入」「支出」の金額カードを押すと、対象月・年、分類・検索条件を保持して選んだ種類の明細だけを表示する。選択中のカードは枠・背景とaria-pressedで示す。「収支」は表示のみで切り替え操作を持たない。切り替え時は表示件数を200件へ戻し、追加表示・空表示の判定は選択種類の件数で行う。上部3つの金額と分類別集計は種類切り替えの影響を受けず、従来の期間・分類・検索条件で全件を集計する。

明細一覧は日付の古い順（1日→2日→3日→5日）、同日は初回登録順（早いものが上）に表示する。`registrationOrder`は新規保存時に既存の最大値+1をサーバー側で付与し、revision CAS・冪等操作と同時に確定する。編集では初回の番号を保持し、クライアントからの番号指定は採用しない。過去日付の追加はその日の最後に入る。CSVにも同じ日付順・登録順を使う。バックアップv2に番号を保持し、復元は安全な非負整数・正の番号の重複を検証する。番号のない旧明細は0相当として従来のID順を保ち、新規明細より先に表示する。旧明細を編集しても0のままとする。過去の正確な登録順を推測せず、既存JSONを利用するためDB migrationは不要。

未分類は入力・検索・設定の候補から外し、既存の未分類明細はその他として表示する。分類のIDと旧バックアップは維持する。大項目の順序は[Money Forward ME公式カテゴリ説明](https://support.me.moneyforward.com/hc/ja/articles/900004380703)の掲載順を使い、中項目の既存IDは変更しない。

中項目は各大項目内で「その他」で始まる項目を常に末尾に置く。通常項目・その他項目それぞれの中では標準項目の既存順を保ち、追加項目を名前の日本語順で続ける。設定一覧と明細入力で同じ順序を使い、追加・名称変更・再読込・旧バックアップ復元後も適用する。

設定の分類は通常時に項目名だけを表示する。「分類を編集」を押すと追加した中項目を選択でき、共通の未保存確認・戻る・背景・Escに対応した編集画面を開く。削除は編集画面内だけに置き、明細で使用中なら理由を表示して無効にする。標準項目と閲覧専用ユーザーには編集操作を提供しない。

残高0円の口座の保管機能は廃止し、0円も通常の口座として保存・表示・集計する。通常の口座保存では旧版から送られた`archived`を無効にする。既存データとv1/v2バックアップのフラグは読み取り互換性のため保持し、基準日未入力の旧保管口座が資産推移を突然欠損させない従来の扱いだけを残す。基準日付き残高の保存時にフラグを解除し、過去の残高履歴・明細・取り込み記録は保持する。

チャートのタッチ操作はHTMLのチャート領域に`touch-action:pinch-zoom`を指定し、1本指の移動をページスクロールに奪わせない。ピンチズームを許可し、ページスクロールはグラフ外で行える。ポインター移動はrequestAnimationFrameにまとめ、最新位置だけを描画する。位置測定は開始時に行い、金額・比較文字列はデータ更新時に準備する。同じ月の再描画を省き、幅が変わらないresize通知ではSVGを作り直さない。期間変更・ログアウト・キャンセル時は保留描画とcaptureを解除する。

メニューは「家計簿」、対象月の上の見出しは「収支」と表記する。登録ボタンは「＋ インプット」、明細登録画面は「インプット」、編集画面は「インプットを編集」と表記する。サービス名は家計簿のままとする。

## 共通の日付・パスキー画面

表示月・明細日・残高基準日は、支払明細と同一の`TRoomDatePicker`と`TRoomDateWheel`で選ぶ。入力欄は下部ホイール、カレンダーアイコンは年・月・日の共通カレンダーへ接続する。戻る・Esc・背景・キャンセル・完了は既存のdialog navigationへ接続し、親の入力と未保存保護を維持する。コピー元と公開コピーは`web-apps.json`の`assetCopies`で管理する。日付の許容範囲は既存APIで検証する。

パスキーは既存の`/security/passkey-client.js`を使用する。アカウント選択は日記と同じ`chooseLinkDialog`、カード配置・文字組み・初期フォーカス・キーボード操作・キャンセル／Escを使用し、家計簿のブランドカラーを維持する。連携先が1件なら選択を省略し、複数なら利用可能な連携先だけを表示して、選択したlink IDのhandoffを引き換える。キャンセル時はhandoffとサービスsessionを発行しない。ログインボタンは請求書管理と同じCSS・アイコンで表示する。認証中はボタン内の文言だけを切り替え、キャンセル・失敗時もアイコンを維持する。

## 認証と共有

既存Security Centerのパスキー、60秒・一回限りhandoff、サービス専用Secret、12時間rolling session、毎回のIdentity／credential／link失効確認、監査を使用する。新しい認証方式・暗号鍵管理・Passwordログインは追加しない。

サービスアカウントは `owner`（田中宏知、編集可能）と `viewer`（田中宏知の共有閲覧用）、`chiharu-admin`（田中千晴、独立家計の管理用）。`owner`だけは既存 `primary-admin` Identityに限定する。追加の管理用と共有閲覧用は、同じアカウントを複数Identityへ明示的に連携できる。同じIdentityに登録した複数パスキーも同じ有効な連携先を利用できる。1つのIdentityとアカウントの組には有効／承認待ちの連携を1件だけ許し、解除後の再連携には新しいlink IDを発行する。Identity・パスキー・連携の停止はそれぞれに紐付くsessionへ適用し、他の利用者の連携を停止しない。千晴の閲覧用アカウントは作成しない。既存の共有閲覧用は千晴のデータを参照しない。氏名は権限の根拠にしない。

サービス連携は第一管理者が直近5分以内の再認証後、既存の招待・承認・サービス連携手順で明示的に設定する。migrationはIdentity・credential・service linkを作成しない。千晴の既存Identityを使う場合も、家計簿の連携はユーザーがSecurity Centerで設定する。

画面はログイン／起動時の`sessionContext`を保護APIの`X-Household-Session`へ送る。別タブでCookieが切り替わると旧画面の読取・変更・書き出し・復元・整理を401で止め、既存のセッション消去処理を使う。ヘッダーは権限を与える資格情報ではなく、署名CookieとSecurityの失効照会が認証の正本。更新前の宏知の画面と旧Cookieだけは、入力を保持して安全に自動更新できるようヘッダー省略を許可し、新しいログインと独立家計には適用しない。

共有用でも検索・集計・書き出しができる。APIは読み取り用と変更用を分け、共有用からの明細・口座・月末残高・分類の変更と復元を403で拒否する。画面でボタンを隠すだけの制御にしない。

## 保存と更新

- `household_accounts`: サービスアカウントとrole・有効状態・session version・所属`household_id`。アプリのバックアップ復元の対象外。
- `household_state`: 家計ごとの現在のデータ世代とrevision。既存家計は`main`、千晴は`chiharu`。
- `household_records`: 世代・記録種別・安定したIDごとのJSON。口座（基準日付き残高履歴を含む）、明細、分類、保存済み月末残高、過去チャートを分離する。
- `household_requests`: 家計IDと操作IDの組・入力のハッシュ・結果。通信再送を家計ごとに冪等にする。
- `household_datasets`: 各世代の所属家計と保管・復元リース情報。読取・復元・整理は所属家計内だけで行う。

家計の選択は保護APIで現在のサービスアカウントから解決し、リクエスト本文・URL・復元ファイルの家計IDを採用しない。migration `0006`は既存データ・revision・再送結果・有効状態を保持して所属を追加し、千晴には標準分類だけを作成する。定期バックアップにも所属情報と両家計の全世代を含める。

更新では期待revisionを必須とし、revisionの連番をDB triggerでも検証する。操作IDの記録、revision更新、対象行の変更を一つのD1 batchで確定し、競合は409で全体をロールバックする。別タブの変更は通知し、古い編集の暗黙上書きを防ぐ。

個々の値は整数円。明細20,000件、口座200件・各内訳100件、分類500件、月末／過去記録はそれぞれ3,600件まで。保存するJSON本文の合計は10MiBまでとし、上限では明示的に拒否する。バックアップのアップロードは16MiBまで、画面のファイル選択は12MiBまで。JSON・D1の上限を超えた不完全な保存を成功扱いしない。

## バックアップと復元

旧平文互換形式は `troom-household` v2（通常の手動出力は上記v3）。日付付き残高履歴を含む。v1の復元にも対応し、基準日不明の旧残高へ推測の日付を付けない。口座・内訳・明細・分類・月末記録・過去チャートを含め、Identity、認証用アカウント、パスキー、Cookie、Secretは含めない。バックアップから権限を作成しない。

復元前に全レコードの型・ID・参照・標準分類・金額・年月を検証する。新しい非公開世代へ50行ずつ準備し、完了後に期待revisionのCASと操作ID保存を一つのbatchで確定する。同時再送も準備世代を分ける。失敗した準備世代や旧世代はそのままではAPIから見えず、現行世代を削除しない。旧世代の削除や自動整理は初版では行わない。

CSVはUTF-8 BOM付き、金額は収入が正・支出が負。内容・メモ等の文字列で表計算の式が実行されないようにする。

## ウェブアプリ

`/household/`をid・開始URL・scopeとするstandalone manifestを配信し、採用されたB案（緑地・白い線画の財布と金のコイン）をホーム画面・Apple touch icon・faviconで使う。`public/icons/`のPNGは承認済み生成画像からサイズだけを変えて作成した。アプリの名称と既存の画面色は維持する。

「設定・データ管理」の「ホーム画面に追加」から、Chrome／Edge等では利用可能な`beforeinstallprompt`を一度だけ使用する。追加・キャンセル・失敗を区別し、追加済みのアプリ内ではボタンを隠す。プロンプトがない場合は、その場で端末に応じたブラウザメニューの手順を表示する。iPhone／iPadはSafariの共有→ホーム画面に追加、PCはインストールまたはSafariのDock追加へ案内する。OSの追加操作そのものを自動実行した扱いにはしない。

オンライン専用を維持し、Service Worker・オフラインキャッシュ・認証データの端末保存は追加しない。既存の共通updaterを使い、未保存入力・データ処理中に加えて追加プロンプト表示中も更新を延期する。manifest・アイコンは認証不要で配信し、APIの権限とno-storeは維持する。登録情報は`web-apps.json`を正本とする。

ブラウザ仕様の参照：[Chromeのインストール条件](https://web.dev/articles/install-criteria)、[iPhoneのホーム画面への追加](https://support.apple.com/en-lb/guide/iphone/iphea86e5236/27/ios/27)。ブラウザfixtureはmanifest・アイコンの読込、Chromiumのinstallability診断、追加イベントの成功／取消／失敗、更新保護、端末別案内、standalone表示を確認する。OSの実インストール・実端末パスキー認証は別の確認とする。

## 検証と初回公開

独立家計への更新では、家計簿 `0006_independent_households.sql` とSecurity `0028_independent_household_accounts.sql` を対象D1へ適用してから対応コードを公開する。バックアップのschema許可リストも同じPRで更新するため、Backup Worker、およびバックアップ処理を組み込むSecurity・Diaryの対応版も公開する。migration前後の版が混在する間のschema不一致は従来どおり保存を停止し、許可リストの検査を迂回しない。

複数Identityでの管理用共有はSecurity `0029_household_shared_accounts.sql`で、アカウント単位の排他indexをIdentity＋アカウント単位の一意indexへ置き換える。既存データ・連携状態・credential・監査履歴は変更しない。Householdとバックアップ処理を含むSecurity・Diary・Backupの対応版を揃え、共有連携の追加前にmigrationを適用する。本番migrationの適用と連携設定はPR作成には含めない。元のindexへ戻す場合は先に複数Identityへの現在の割り当てを確認する。重複がある状態で旧indexを再作成したり、連携を自動解除したりしない。

```sh
pnpm run check
pnpm test
# ルートから、合成データとローカルSQLiteだけで実施
node household-worker/test/household.browser.mjs
node tools/verify.mjs --target household --build
```

単体試験は残高と収支の独立、共有用権限、実Security連携、migrationの削除範囲と保持データ、再送・競合、壊れた復元・準備中の失敗・同時復元を検証する。チャートの暦月フィルター、欠損月の前月比、ゼロ・マイナス・大きな値の軸も確認する。ブラウザfixtureは1440px・390px・320pxで、52か月の合成記録を使った初回表示・タブ遷移・リサイズ・期間選択・ホバー中の軸固定・バー非表示・期間別比較・内訳削除確認と並び替え保存・金額入力のカンマ表示・タッチ／キーボード選択・文字の領域内表示・閲覧専用・ログアウト消去を確認する。実端末WebAuthnの操作とは区別する。

初回は専用D1に `0001`〜`0003` を適用し、専用 `SESSION_SECRET` を安全な乱数で新規設定する。既存Secretは上書き・共有しない。Securityのサービス追加migrationは既存データと外部キーを維持し、利用者へのアクセスを自動付与しない。既存のSecurity Centerで第一管理者が編集用・共有用の必要な連携を設定する。

初回のWorker作成・route・D1・Service Bindingの準備は、通常のversion昇格とは別のインフラ手順で行う。既存サービスのrouteを変更しない。コード公開は対象CIが成功したmainを使用し、Securityと家計簿の双方が準備できた後にインデックスへ入口を公開する。切り戻しでは新規D1や記録を削除せず、入口を戻し、サービスを停止または修正版へ進める。

## 認証失効と履歴整理

401/403、明示ログアウト、別タブのログアウト、セッション期限で共通の初期化を実行する。台帳、チャート、編集中の入力、復元用ファイル、確認コールバック、ダイアログと履歴のスナップショットを消去し、通信を中断する。失効前の応答は世代番号で破棄する。通信障害だけなら入力を保持するが、ログアウト操作は通信障害でも端末の表示を消去する。30日の期限はタイマー上限を超えるため、上限付きで再確認する。認証方式、Cookie、鍵、サーバーの有効期間は変更しない。

設定の「古い履歴の整理」はオーナーだけが実行できる。再送履歴は90日より前、未使用世代は30日以上前を候補とし、現行世代、復元リースが有効な世代、直近3世代を除く。日時はUTC、日単位で保守的に切り下げる。候補を表示して確認後にのみ削除し、1回1,000履歴・10世代までとする。候補の指紋とrevisionを再照合し、削除・revision更新・操作の再送記録を同じトランザクションで確定する。90日を超えた操作IDの再送保証は行わない。未保存の古い操作を自動再送しない。

migration 0005は世代メタデータと検索indexを追加するだけで、既存の家計データ・再送履歴を削除しない。既存の世代はmigration適用時刻から最低30日保管する。移行前の世代の順序は判別できないため、同時刻の場合はIDを並び順に使う。復元は各chunkで1時間のリースを更新し、切替と旧世代の退役を原子的に記録する。公開時に整理APIを実行しない。追加テーブルも既存の定期バックアップに含める。
