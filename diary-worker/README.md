# 日記 Worker

`/diary/` のWeb、API、PWAを配信する。認証・鍵・公開手順の正本はリポジトリの `docs/security/passkeys.md`、`docs/browser-support.md`、`docs/development-flow.md` を参照する。

## 起動

HTMLは共通Updater、Passkeyクライアント、軽量な `diary-bootstrap.js` を読み込む。`/api/session` で現在の認証と権限を確認し、未ログインなら本体を取得せずログイン画面を表示する。Passkey成功またはsession再開後に、本体・日付選択・モーダル処理を読み込む。

本体は信頼できるsessionの権限を適用し、前のデータを消してからヘッダー・検索・一覧のローディングを表示する。検索・本文表示・天気のモジュール準備と初期データ取得を並行する。操作の受付は必要なモジュールとイベント設定の準備後に開始する。写真処理／アップロードは最初の写真選択まで読み込まない。本文のrich text処理は一覧・詳細の表示にも必要なため、本体とともに準備する。アルバムは開いた時点で従来の写真APIを呼ぶ。

`GET /diary/api/bootstrap` は、検証した同じsessionを使って `session`、`households`、`meta`、`entries` を返す。`entries` の検索・日付・月・タグ・お気に入り・下書き・ゴミ箱・ページングは既存 `/entries` と同じ処理／権限判定を使い、写真本体や詳細写真一覧は含めない。既存APIは維持する。初回は `/session` と `/bootstrap` の2往復を使い、データ取得前に安全な画面枠を表示できるようにする。再開の監査は従来の `/session` で記録する。

bootstrapもrequestごとに現在のSecurity状態を検証し、同じGET requestの内部だけで検証結果を再利用する。foregroundのbootstrapは置き換え元の一覧GETと同じRolling Session更新条件を維持する。バックグラウンド・エラー・session確認だけでは延長しない。遅い応答は検索のrequest IDとsession／householdの世代で区別し、ログアウト後や切替後に前のデータを再表示しない。

写真ビューアの読み込み・画像切り替え・スワイプ・矢印キーは `public/diary-photo-viewer.js` が担当する。選択中の写真と戻る履歴、閉じる要求、認可・アップロードは本体側で管理し、ビューアには表示要素と写真選択だけを渡す。認証後に先読みするが、一覧描画や編集準備の完了条件には含めない。未準備の写真操作だけが読み込みを待ち、閉じる・session切替後に遅れて表示しない。

写真は画面全体に収め、操作を上下に重ねる。左右の矢印ボタンは置かず、等倍では左右スワイプ／左右キーで写真を切り替える。ピンチ、マウスホイール、ダブルクリック、＋・－キーで1～6倍に拡大・縮小し、拡大中はドラッグ／矢印キーで画像内を移動する。表示中の倍率ボタンまたは0キーで等倍に戻す。倍率と移動量は写真切り替え・閉じる際にリセットし、画像の表示範囲に合わせて移動量を制限する。対応ブラウザでは全画面ボタンからFullscreen APIも利用でき、解除後も写真表示を維持する。表示用画像の長辺上限1800pxと既存の保存操作は維持する。

## 位置復元と戻る際の取得

新規表示の先頭移動は軽量bootstrapで認証待ちより前に行い、初期データ取得後には行わない。戻る/reloadのsnapshotがある場合はブラウザ標準復元との競合を避けて手動復元し、保存した検索条件・読み込み済み件数を揃えてからIDアンカーとタグ内部位置を反映する。従来の件数上限2000件と月展開の取得上限100ページは維持する。各requestの上限50件の範囲でbootstrapから必要件数を続けて取得し、途中の一覧を確定・再描画しない。以後の「さらに表示」は確定したoffsetから継続する。

復元のframeとフォント読み込み後の補正は世代で管理し、wheel・touchmove・pointerdown・スクロールキー、検索変更、session切替、pagehideで取り消す。プログラムからも発生するscrollイベントは取消条件にしない。ルートのCSSをautoにして標準History・共通dialogの復元もアニメーションさせず、日記の位置反映にはinstantを明示する。初期一覧・メタ描画時には、その同期処理直前のスクロール位置を維持する。BFCacheは生きたDOMとブラウザ位置を利用し、古いsnapshotを再適用しない。pagehide時に完成済み表示の条件と位置を保存してreload/進むにも利用する。本文・写真の永続キャッシュは追加しない。

月別一覧と写真検索は既存のhousehold/date indexで走査範囲を絞れる文字列範囲を使う。下限は7文字のmonth、上限はその末尾ASCII数字の次文字（例：`2026-10`以上`2026-11`未満、`2026-09`以上`2026-0:`未満）。カレンダーへの変換を避け、旧データや不正月も以前の`substr(...,1,7)`と同じprefix一致になる。月別件数・タグ集計・お気に入り・並び替えは変更せず、追加indexやmigrationは不要。

ブラウザを起動しない追加検証は `node tests/startup-state.mjs`（入力・非同期復元・取得世代と一括描画）と `node tests/month-range.mjs`（メモリ内SQLiteの旧条件との結果一致・query plan）。実機のレイアウト、BFCache、PWA、操作感や性能は別途確認が必要。

## アルバムの表示上限

初回48枚を取得し、「さらに表示」で96枚ずつ段階的に取得・追記する。全年月・月指定・検索のいずれも、1つの一覧に表示する累計上限は4,800枚とする。再試行や連打でも上限を超えず、残りがある場合は年月・検索条件での絞り込みを案内する。1回の追加処理はページ取得後に経過8秒以上なら区切り、続きは「さらに表示」から再開する（進行中の1リクエストは待つ）。サムネイルの遅延読み込みと写真から戻る際の位置復元を維持する。上限は保存できる写真の総数を制限しない。

## 写真の送信と復旧

保存済みの `excludedPhotoIds` は下書きの写真除外状態として保持し、編集を開いたときに写真DELETEの待ち行列へ入れない。今回の編集で明示的に削除した既存写真だけを別の一時的な待ち行列で扱い、削除の成功・編集破棄で消去する。編集下書きの公開時はサーバーの公開トランザクションが除外を適用するため、後続の写真反映に失敗してもDELETEを再実行しない。

写真の準備は、元画像の読み込み・コピーと縮小画像の生成を分離する。変換中の1枚と次の1枚までを読み込み、未変換の原本サイズ合計が16MiBを超える先読みはしない。16MiB超の原本は単独で処理する。この上限は先読みする原本の予算であり、ブラウザ全体のメモリ上限ではない。写真選択欄は準備の完了後にクリアし、選択順と原本のbytes・EXIFを保つ。

元画像の読み取りが `NotReadableError` で失敗した場合のみ150/450ms待機して最大3回試す。権限・容量確保の失敗を自動再試行せず、読み取り、コピー、デコード、変換の失敗段階を分ける。選択元の参照が無効な場合は同じ参照への再試行で直るとは限らないため、成功分と本文を保持して失敗した写真だけの再選択を案内する。失敗一覧は件数と最大3ファイルの詳細にまとめる。準備時のconsole診断は段階・既知の例外クラス・試行回数だけとし、元の例外messageやファイル名を出さない。

写真の順序は本文内の写真参照位置を基準とする。日記の拡大表示は本文と同じ順、アルバムは日記の日付・公開順と本文内の順序を逆にした新しい順で表示する。並列アップロードの保存完了時刻では並べない。本文に参照のない旧写真は従来の保存順で本文末尾に続ける。月別アルバムだけ、並び替えアイコンで新しい順／古い順を切り替えられる。「すべて」に戻ると新しい順へ戻し、アイコンを隠す。保存データの変更・移行は不要。

選択時に元ファイルのbytesをメモリ内のFileへ確保し、写真提供元・端末上のファイルが後から変更されても同じ内容を送信する。元画像、EXIF、ファイル名は維持し、本文・写真を永続ストレージへ平文保存しない。送信中の合計16MiB以内で最大3件並列とする。合計が枠を超える次の写真は空きを待ち、Save-Data/2G、通信障害後の同じ編集セッションでは1件ずつ送る。16MiBを超える単独の写真も1件ずつ送る。画像サイズに応じた送信タイムアウトは3〜15分、保存確認は10秒で打ち切る。

通信例外、408、429、5xx、成功応答の破損は最大4試行、1/3/7秒を基準とするジッター付きバックオフで扱う。429/503のRetry-Afterは秒数・HTTP日付に対応し、同じ編集セッション内で待機期限を共有する。30秒を超える待機は編集を保持して利用者に再試行を案内する。401/403等の他の4xxは自動再試行しない。投稿操作が既に進行中の送信を待った場合、失敗直後にさらに全試行を繰り返さない。

応答消失時は `GET /api/photo-upload-sessions/:sessionId/photos/:photoId` で同じaccount・householdが所有する有効な一時保存を確認し、保存済みなら本体を再送しない。確認できなければ同じ写真ID・セッションで既存の冪等な送信を再試行する。確認APIはIDだけを返しno-storeとする。既存のD1確定・試行ごとのR2 key・commit・本文中の写真参照確定の順序は維持する。

失敗時は編集画面と未送信の写真をメモリに残し、完了済み写真は再送しない。編集画面で401を受けても入力を初期化せず、別タブで同じアカウントへ再ログインして再試行する案内を出す。サーバーの認証・認可は全リクエストで従来どおり実施する。ブラウザ・タブを閉じた場合の復旧を保証する機能は追加していない。

写真commit確定後の写真一覧取得と一時保存台帳のcleanupは並行する。両方の完了を待って応答し、写真の確定順序・冪等性と正式写真を消さない保護を維持する。

API応答の`Server-Timing`は`diary_total`（Workerでの総時間）、`diary_auth`（同request内の認証確認の合計）、`diary_handler`（初回認証を含むhandler）、写真送信時の`diary_receive`（multipartの受信・解析）、`diary_store`（3種類のR2保存を待った時間）をミリ秒で返す。authはhandlerと重複するため全指標を単純加算しない。受信待ちには上り転送が含まれ、R2保存時間だけを回線の時間と解釈しない。

投稿・下書き保存ごとに、ブラウザのconsoleへ`Diary save timing`を1件出す。ボタン操作からの総時間、準備待ち・送信待ち・本文保存・写真確定・最終反映・一覧更新、APIの所要時間とServer-Timing、写真ごとの準備時間・送信容量・順番待ち・試行時間を含む。写真の準備・送信は保存ボタンより先に始まるため、写真ごとの時間をボタン操作後の時間へ加算しない。編集開始からのユーザー操作時間を通信時間として扱わない。

失敗時の匿名の送信試行UUID、段階、HTTP status、例外分類、経過時間、Cloudflare Ray IDのconsole出力も維持する。これらの診断にはファイル名・本文・画像・Cookie・token・account/entry/photo IDを含めず、新たなログ収集先や永続保存設定は作らない。詳細調査と制約は[2026-10-23の調査記録](../docs/history/diary-photo-upload-20261023.md)を参照。

## キャッシュと更新

Service Workerは登録された正確なbuild付きの公開JS／CSS／アイコンURLだけをcache-firstにする。install時の先読みはログイン入口に必要な資産だけとし、本体や写真モジュールは利用後に保存する。API・HTML・写真・投資資産・manifestはこのキャッシュを経由しない。エラー、redirect、private、no-store応答は保存しない。

Diary Workerの公開静的資産で `v=diary-` と12桁hexのbuild IDがあるJS／CSS／PNGは `public, max-age=31536000, immutable`。HTMLは `no-store`、SW本体は `no-cache`、manifestと未version資産は従来の1時間。投資資産とR2写真の認可・配信方針は別に維持する。build同期は `node tools/sync-web-app-builds.mjs --target t-room-diary` を使う。共通Updaterと未保存入力・処理中の更新延期も維持する。

## 起動の検証

`pnpm run test:startup` は起動契約、実SQL／Security連携のbootstrap、静的キャッシュ、cold／warm／Passkey模擬／再開／standaloneのローカルブラウザfixtureを実行する。恒久的な性能計測や個人追跡は追加しない。模擬試験は実端末のWebAuthn・PWAの性能を代替しない。[初回比較と制約](../docs/history/diary-startup-performance-20261016.md)を参照。

## バックアップの管理

D1単独v8へ移行し、03:25 JST・日次30世代・月次12世代を維持する。写真のコピー・検証・R2障害はD1保存の成否に参加しない。写真のR2→R2差分保存は別Cronで継続し、新着優先、独立した再検証枠、期限付き追いつき、R2上のリース/カーソルを使う。旧v7以前・旧写真は自動削除しない。D1と写真の状態はT-Cloudの`Backup-data`に分離表示し、全体復元には写真参照との照合が必要。復元時のaccount無効化は維持する。方式・時刻・上限・隔離復元・公開前提は[バックアップ運用](../backup-worker/README.md)を参照。
