# T-Cloud ゴミ箱の保持期間と完全削除

## 現行との差分

従来の単体完全削除は、読取後の状態を再確認せずR2を消し、最後にIDだけでD1を削除していた。一括削除もR2削除中の復元を防げず、最後にゴミ箱フォルダをまとめて削除していた。フォルダ復元は削除日時だけでグループを識別していた。既存の日次Cronは古いmultipart uploadの中断用で、ゴミ箱の期限削除はなかった。

新規ゴミ箱移動は、サーバーのUTC時刻とランダムUUIDをD1の同一batchに記録する。ファイル・フォルダ・削除申請承認を対象とする。フォルダ配下は同じ世代にそろえるが、すでにゴミ箱にある別世代は上書きしない。復元時は世代を解除し、再移動で新しいUUIDと期限を作る。作成・更新・アップロード日時は期限に使わない。

既存Cron（毎日18:17 UTC／翌日03:17 JST）を再利用する。自動削除は720時間経過後の定期処理で実行する。追加Cron、R2 Lifecycle、暗号化・認証・権限の変更はない。日記バックアップは別Service Bindingの読み取り専用マウントであり、この削除対象に入らない。ゴミ箱はバックアップではなく、R2から完全削除したオブジェクトをD1の復旧だけで取り戻すことはできない。

## 状態と競合

1. 有効なoperationと一致する削除日時を持つ対象だけを候補にする。旧データのoperationはNULLのまま保持する。
2. 候補取得後も、ID・削除日時・世代・現在のキー・ready状態を条件に、永続manifestをINSERTする。トリガーで同一トランザクション内にキー共有・配下の整合性を再検証し、ファイルを固定し、世代を不可逆状態にする。監査記録も同一batchに含める。
3. 復元が先に成立したら条件不一致でclaimしない。claimが先なら、復元・世代変更・ファイル更新をD1トリガーが拒否し、APIは409と説明を返す。フォルダ復元はbatch全体をrollbackする。
4. R2本体・暗号化サムネイル・表示用サムネイルを重複キー排除後に順次削除する。すべて成功するまでファイルD1レコードを消さない。
5. manifestのphaseをobjects_deletedへ進め、条件付きD1削除・completedへの移行・成功監査を同一batchで確定する。Worker停止・D1障害後も同じmanifestだけを再試行する。

manifestは完了後も保持し、キー／Stream UIDの新規参照・再利用をD1トリガーで拒否する。他ファイルの本体・サムネイル・表示用サムネイル・Stream UIDとの共有は、相手がゴミ箱内でも削除を拒否する。manifestは削除・書換禁止。R2とD1をまたぐ原子性を仮定しない。[D1 batchのトランザクション仕様](https://developers.cloudflare.com/d1/worker-api/d1-database/#batch)に基づく。

一部削除後は元データが揃っている保証がないので、同世代全体と削除済み子要素のある親フォルダの復元を拒否する。空フォルダの完全削除にも永続記録を残す。無理にpurge_idを解除しない。

手動完全削除・一括削除も同じclaim／manifestを使うが、30日条件やoperation必須条件は課さない。通常ファイルは常に対象外。管理者の既存canDeleteを必須とする。自動モード無効時も、明示的な手動削除と失敗後の手動再試行は可能。

## フォルダと上限

自動処理は、削除済み祖先から配下全体を再帰検証する。通常保管・復元済み要素、ready以外のファイル、異なる世代／削除日時があれば、そのツリーを削除せず実行を中止する。独立して古くからゴミ箱に入っている子要素を、新しい親の期限に合わせて消さない。異常な混在は人による確認が必要。

ファイルは上限内の小分けで処理する。フォルダは子ファイル・子フォルダのいない葉だけを条件付き削除し、次の実行で親へ進む。大きなツリーを一度にD1物理削除しない。最初の不可逆処理が確定した世代は、処理が次回へ残っていても通常復元できない。

| 設定 | 初期値 | 意味 |
|---|---|---|
| TRASH_CUTOVER_MODE | maintenance | 移行中はゴミ箱の移動・復元・一覧・完全削除を503で停止。readyとD1承認の両方が必要 |
| TRASH_RETENTION_MODE | disabled | disabled／dry-run／enabled。それ以外は停止 |
| TRASH_PURGE_EMERGENCY_STOP | false | true等、false以外なら手動・自動の完全削除を停止 |
| TRASH_PURGE_MAX_COUNT | 20 | 自動実行1回のファイル＋フォルダ上限 |
| TRASH_PURGE_MAX_BYTES | 104857600 | 自動実行1回100MiB。本体＋関連R2 HEAD容量、再試行manifest容量も計上 |
| TRASH_PURGE_MAX_CANDIDATES | 200 | ファイル＋フォルダ候補総数の異常上限 |
| TRASH_PURGE_GROWTH_FACTOR | 3 | 前回候補数に対する増加倍率 |
| TRASH_PURGE_GROWTH_ALLOWANCE | 20 | 急増停止の増分許容量 |

件数・容量上限は未claimの対象を次回へ残す。1ファイルだけで容量上限を超える場合もclaimしない。手動は既存と同じ1リクエスト20ファイルまでとし、自動用容量制限は課さない。空フォルダも1リクエスト最大20件の範囲内で処理し、Webは残件数に従って次を呼ぶ。

候補総数が絶対上限を超える、または前回比倍率と増分許容量を両方超える場合は、D1 controlのemergency_stopを1にして停止する。初回も絶対上限を適用する。D1照会失敗・状態矛盾・外部ストレージ障害・監査保存失敗時は次の対象へ進まない。controlが欠落している場合も実削除しない。

手動・Cron共通のD1条件付きleaseを10分取得する。重複実行は停止／409となる。各外部削除とD1削除の直前にleaseと緊急停止を再確認する。Workerが消失したleaseは期限後に再取得できる。期限前に開始した外部I/Oまで取り消すことはできないが、完了manifestの永久予約と復元禁止によって、遅延処理も同じ世代・同じキーしか削除できない。

Streamは現行wranglerにbindingがなく、容量と削除冪等性も実環境確認していない。自動処理ではStream UIDを持つ対象を停止させる。手動でもbinding欠落時はR2削除前に停止する。将来Streamの自動削除を追加する場合は、容量検証と「既に不存在」を成功とするadapterを合成fixtureと隔離環境で検証してから別途レビューする。

## ドライラン・監査・表示

disabledではCronから新しいschemaへ一切アクセスしない。dry-runでは候補の整合性を確認し、監査とcontrolのlease／前回候補数だけを更新する。ファイル・フォルダ・operation・manifest・R2・Streamは変更せず、不可逆状態へ進めない。容量はD1上の参考値で、実R2容量の検証はenabled時のHEADで行う。キー共有等のclaim時検証、R2削除結果はドライランの成功だけでは保証できない。

cloud_audit_logsのtrash_run_started／trash_run_finished、trash_dry_run_candidate、trash_purge_claimed、file_deleted／folder_deletedで追跡する。実行ID、時刻、対象ID、世代ID、候補数・参考容量、成功／失敗／スキップ数、削除容量、中止理由を記録する。予期しない例外も完了監査へ記録し、D1監査自体が不能な場合はrunIdと理由だけをconsole.errorへ出す。オブジェクトキーや暗号鍵をログへ出さない。中途停止で完了監査がない実行は開始監査とmanifestで調べる。

ゴミ箱カードに720時間到達日時と無効／試行中／有効を表示する。旧データは自動削除対象外、不可逆状態は復元不可と表示する。日時は「削除実施の確約」ではなく対象になる最早時刻であり、上限・矛盾・停止設定によって後ろにずれる。

## 導入・有効化

**0013を旧Workerへ先に適用してはいけない。** 旧WorkerはR2削除後にD1を削除する。0013のDELETE保護は旧方式を拒否するため、R2だけ消えた状態を作り得る。単体・一括の両方で、過去の実コードと合成データから再現済み。旧版へ先にマイグレーションを適用する従来手順は撤回する。

1. PRと対象CIを確認する。本番データを使った削除試験は行わない。旧Workerのバージョンを記録し、進行中の手動削除・一括削除・復元がある場合は完了を待つ。
2. **マイグレーション前に**新WorkerをTRASH_CUTOVER_MODE=maintenance、TRASH_RETENTION_MODE=disabledで100%公開する。schema未適用でも通常ファイルの読み取り等は維持し、ゴミ箱の移動・復元・一覧・完全削除・削除承認は503で停止する。新旧方式を併用するfallbackはない。
3. Cloudflare deploymentが新version 100%であること、公開build一致、GET /cloud/api/trash-transition-statusのmode=maintenance、operationsAvailable=falseを読み取りで確認する。停止前から旧版で始まった削除・復元要求の終了も確認する。**新versionの公開完了だけで既存要求の終了を保証したことにはしない。終了を確認できなければ0013を適用せず、停止状態を維持する。** 一定秒数待つだけで終了と決めない。
4. 本番マイグレーションの明示承認がある場合だけ、既存の適用履歴を確認して0013を専用手順で適用する。既存行を更新・backfillしない。control.cutover_readyは初期値0であり、schemaが揃ってもゴミ箱操作は再開しない。部分適用・DB照会失敗・必須トリガー欠落でも503を維持する。
5. schemaReady=true、cutoverReady=falseを読み取り確認する。移行対応版以外へrollbackしない。必要ならTRASH_CUTOVER_MODE=readyの版を100%公開し、build/versionを確認する。この時点でもcutover_ready=0なので停止したままとする。
6. 旧版の要求が終了し、新版だけが処理することを確認した移行担当者が、最後にcontrolのid=1へcutover_ready=1を条件付きで設定する。GET状態確認のoperationsAvailable=trueとretentionMode=disabledを確認する。これで既存の手動ゴミ箱機能のみ再開する。自動削除の承認とは別の操作である。
7. 将来の自動削除は別途承認後にdry-runへ変更し、複数回の監査と対象ID・世代・期限・旧データ除外を確認する。隔離環境の合成データで障害・競合・再開試験を行い、さらに別途明示承認後だけenabledへ変更する。

停止制御は新schemaへの書込より前、かつR2のHEAD・削除やStream操作より前に評価する。modeが未指定・不正の場合も停止する。DBのcutover_ready=1と完全なschema確認だけではmode=maintenanceを解除しない。D1側の切替承認を0へ戻せば、既に開始した新方式の削除も次の外部操作直前に停止する。ただし開始済み外部I/Oの取消はできない。

状態確認APIはbuild、移行mode、schema／切替承認の成否、自動削除modeのみを返し、ファイルID・件数・キー・認証情報は返さない。本番の停止確認にDELETE／復元APIを使わず、GETとdeploymentの読取を使う。

本番DB操作の承認がない場合は、コードのmaintenanceでの先行公開と停止維持までにとどめる。本番0013の適用と切替承認を、通常のコード公開から自動的に実行しない。

緊急停止はcontrolのemergency_stop=1を管理者のDB管理経路で設定する。各オブジェクト削除直前に照会するため、Workerの再公開を待たず停止できる。環境変数の停止設定とdisabledも併用する。停止済み外部I/Oは取り消せず、既に消したデータは戻らない。対処後の再開ではmanifestを保持し、同じ対象だけを再試行する。原因を調べずemergency_stopを解除しない。

rollbackはまずcutover_ready=0／maintenanceでゴミ箱操作を停止し、次に安全なコードをforward fixする。旧コードへ単純に戻すと復元競合保護を失うため、claim済み行・トリガー・manifestを残す。失敗行のpurge_id、operation.purge_started、manifestを消して「復元できる」状態に戻さない。D1 Time Travelだけでは削除済みR2は回復しない。

旧データは自動backfillしない。利用者が内容を確認して復元し、改めてゴミ箱へ移動したものだけ、その新しい操作時点から720時間を数える。大量の旧データを移行する必要があれば、対象一覧・完全バックアップ・所有者確認・新しい猶予期間を伴う独立した移行を別途設計する。

## 検証範囲

tests/trash-retention.mjsは全migrationを空のSQLiteへ適用し、実SQL、トリガー、batch rollbackとR2呼出記録で検証する。候補取得後・HEAD後・削除中の順序を制御し、復元／再移動／フォルダ復元／Cron重複／手動競合、R2障害、claimとfinalize時のD1障害、外部削除後のWorker中断とlease期限切れ再開、旧データ、容量・件数・急増停止、権限、ドライランの業務データ無変更を含む。

tests/trash-retention-runtime.mjsではローカルworkerdの実D1／R2 bindingへ全migrationを適用し、claim監査失敗時のトリガー書込を含むrollback、R2削除後のD1失敗・復元拒否・再試行、キー再利用拒否と空フォルダ削除後の親復元拒否も検証する。

本番削除、実Cloudflareでの障害注入、実Stream、実端末でのゴミ箱表示は行わない。Node SQLite fixtureは本番分散環境の実行保証そのものを代替しない。有効化前の隔離環境での検証と明示承認を必須とする。
