# T-Cloud Windows同期設計

2026-11-19更新。利用者の実作業開始指示と、HDDの実際の保存先でも削除非表示を必須とする回答を受け、Windows互換性のfixture実装・検証を進めた。全原本のHDD保存、名前変更、内容の上書き、HDD側の削除禁止、オンライン削除の反映を目標とする。管理者の実パスキー互換性は確認済み。Windows同期アプリは開発段階で、実データ同期はまだ接続していない。

今回の実装はWindows・外付けHDDの連携を対象とする。T-Cloud本体の既存の表示・画面設計・Web上の再生方法は変更しない。以下の過去の検討にあるゴミ箱の表示・ページングの提案も、表示変更の実装許可とは扱わない。

Windows Server 2025のCIでは、部分取得中のファイルを非同期で読み直すと`0x8007017B`になる。Windowsのイベント方式のReadFileでも確認でき、.NETの版だけの問題ではない。復号単位全体の保持・取得通知からの非同期処理・キャンセル対応を実装したが、大きいファイルの部分取得中の問題は残る。CF_HYDRATION_POLICY_FULLは同じ3MiB／24MiBファイルの任意位置読み取りを3回ずつ実行し、実機とCIの両方で通過した。2026-11-18に利用者は「はい、HDD側は保存完了後に開く」と了承したため、Windows初期版はFULLを採用する。一覧と名前を先に表示して全原本の取得を進め、未取得のファイルをWindowsアプリから開く場合は本体全体の取得完了を待つ。取得済みファイルはHDDから開く。この方針はWindowsとHDD側だけに適用し、T-Cloud Webの表示・再生は変更しない。運用対象のFULLをCIで検査し、PROGRESSIVEは明示的な比較診断として残す。PROGRESSIVEの問題が解決したという扱いにはしない。

## 利用者の指定

- 保存先は選択可能。外付けHDDはNTFS／固定ディスクとして認識される媒体を初期対象とする。以前検査したWD Elements 25A2、約2TB、D:を使う場合も、実装時に接続と媒体識別を再確認する。
- バックアップ対象の全原本をHDDに順次取得し、取得完了後は通常のファイルとしてオフラインで利用できる。取得済み本体は平文で保持する。オンラインの本体変更を継続的に取り込む。
- 保存済み原本は一時キャッシュではなく、期限なしのローカル保存とする。ログアウト、アプリ停止、再起動、通信断やWebセッション期限切れで消去・暗号化・取り出し制限を行わない。ローカルで開くためのパスキー認証は要求しない。空き容量対策等による自動退避・脱水も行わない。確認済みのWeb削除をHDDへ反映する既定の仕様は維持する。
- Windowsのオンライン同期は初回認証・端末登録後の自動継続を目標とする。利用者の2026-11-18の指示に従い、通常のWebパスキーセッションを永久化せず、Windows HDD連携専用の長期端末認可を追加する。Webの表示・パスキー登録承認・通常ログイン期限は変更しない。
- HDDに追加した新規ファイルをアップロードし、既存ファイルの名前変更と、対応アプリで編集した内容の上書き保存をオンラインにも反映する。「タイトル」はエクスプローラーとT-Cloudで表示するファイル名として扱う。
- 上書き保存の検証対象はOffice関係とする。Word・Excel・PowerPointを代表候補に、利用環境での通常保存と連続保存を確認する。名前変更の対象は現在保管している写真・動画を中心とする。
- 内容更新で置き換わる旧版はT-Cloudオンラインのゴミ箱へ退避し、30日経過後の自動完全削除対象とする。HDD上のゴミ箱への旧版保存は採用しない。
- 旧版の復元は別名のファイルとして行い、現在の最新版も保持する。復元したファイルは通常の同期対象としてHDDにも取り込む。
- HDDの実際の保存先フォルダから開いても、右クリックの「削除」を表示しない。専用表示内だけの非表示では要件を満たさない。利用者によるローカル削除を拒否し、削除操作をオンラインのWeb画面へ集約する。ファイル・フォルダをHDDだけの取得対象から除外する方式は採用しない。
- オンラインでゴミ箱に移したファイルは、確認後にHDDの同期フォルダからも削除する。削除済みのIDを再アップロードしない。
- オフライン編集と別端末更新が競合したら両方を保全する。
- HDD未接続・I/O失敗・権限失効・不完全な一覧は削除の証拠にしない。同じドライブ文字の別媒体には処理を継続しない。
- 初期版の対象はT-Cloudとする。日記写真のHDD取り込みは既存のアルバム保存機能で扱う。

## 推奨する操作仕様

以下は指定内容を具体化する設計。Windows側は実パスに適用するネイティブShellフォルダ拡張とCFAPIの組合せを検証中であり、製品への常設登録はまだ行っていない。

| 操作・状態 | 動作 |
| --- | --- |
| 初回ログイン | 一覧を先に作り、閲覧権限のある対象フォルダの全原本を順次取得する。全件取得が完了した時点を表示する |
| 追加アップロード | コピー中・保存中のファイルを待ち、安定した内容を端末内で暗号化して送信する |
| 名前変更 | 同じオンラインfile IDの名前を変更する。内容を変更していない場合は本体の再送を省く |
| 内容の保存 | 同じfile IDの新しい版として送信し、更新前のオンライン版を別のゴミ箱項目へ退避する。名前と内容を同時に変えた場合も、その両方を含む版を確定する |
| 移動 | 同じ認可範囲内の同期フォルダ間では、同じfile IDの移動として扱う。同期フォルダ外へ持ち出す操作はコピーを使い、元ファイルを消す移動は拒否する |
| HDD側で削除 | 右クリックの「削除」を非表示にする。Deleteキー・Shift+Deleteなどの削除要求も拒否し、Webでの削除を案内する |
| 同名ファイルの配置 | 既存のオンラインfile IDと現在の版を確認し、既存ファイルへの上書きとして処理する。関連付けが確定できない場合は保留する |
| オンライン削除 | 削除状態を確認し、HDDの対応するファイルを同期場所から取り除く。開いているファイルの処理は使用終了を待つ |
| オンライン削除と未送信編集の競合 | 編集版を同期対象外の回復フォルダに保全してから同期場所を更新する。回復コピーは手動で戻すまで保持する |
| 同期用アクセス権の期限切れ | 登録済み端末の証明で自動更新する。通常の期限経過ではパスキー入力を要求しない。通信できない間は反映を保留し、HDDの取得済み本体と未送信編集を保持する |
| 端末認可の失効 | オンライン同期を停止する。HDDの取得済み本体は引き続き認証なしで利用できる。本人が再登録した場合は、オンラインの差分と削除を確認してから未送信の編集を送る |

同期履歴の破損・消失や別PCへの移行時は、先に既存ファイルとオンラインの状態を照合し、空の履歴から自動アップロードを始めない。外部からファイルが欠損した場合も、オンラインの削除状態とローカルの未送信編集を照合して回復を判断する。

更新の即時性は、HDD接続・有効な認証・通信・空き容量が揃っている間の自動反映として提供する。数分以内を検出の暫定目標とし、大容量ファイルの転送完了時間は別に表示する。状態には最終同期確認時刻、取得・送信待ち件数、保留理由を含める。

オンライン削除をHDDにも反映する運用では、復旧はT-Cloudのゴミ箱と回復用コピーに依存する。オンラインの完全削除後も全原本を保管する世代バックアップが必要な場合は、別の保持仕様を設ける。

## 名前変更と上書きの整合性

- オンラインfile IDを正本の識別子とし、Windows側の名前・パス・ファイルIDとの対応と、最後に同期を確認したオンライン版を記録する。同名ファイルや同じ秒の更新日時だけでは同一性・版を判断しない。
- アプリの一時ファイル保存、元ファイルとの置換、短時間の連続改名をまとめて判定する。置換でWindows側のファイルIDが変わった場合も、追跡できる保存操作は既存オンラインfile IDの更新へ結び付ける。判定できない場合は保留し、既存原本を上書きしない。
- 保存が落ち着いた版を転送用に固定する。送信中に次の編集が始まった場合は、その編集を未送信のまま保持して次の版として処理する。送った版への成功応答だけで後続編集を同期済みにしない。
- 更新前のオンライン版が一致する場合だけ内容・名前・鍵envelope・参照先をまとめて確定する。別端末の更新・改名・移動が先に確定した場合は競合として両方を保全する。オンラインのゴミ箱に入ったIDを更新で復活させない。
- 新しい暗号文本体を別objectへ送信し、保存内容を確認してからオンラインの参照を切り替える。ダウンロード時も同じfile ID・内容版に固定し、取得途中で別の版を混ぜない。HDD上の反映前にサイズと暗号認証を確認する。
- 現行APIは0バイトのアップロードを拒否する。編集途中の一時的な空ファイルは送信を待つ。意図的に空で保存する操作への対応は、暗号形式・既存利用者への互換性を検証したうえで実装する。
- 名前変更・更新・新規追加は既存のフォルダ権限とファイル安全性ポリシーに従う。ドキュメント内部の文書タイトルや動画の埋め込みタグは、利用した編集アプリの保存内容に含まれる。

## 上書き前の旧版をオンラインのゴミ箱へ保存

利用者は、更新前の旧版をT-Cloudオンラインのゴミ箱へ移し、30日経過後に自動完全削除する運用を指定した。内容が更新されてオンラインへ正常に確定した版ごとに、その直前の成功済み版を退避する。版数だけを理由とする保持上限は設けず、各版の退避時刻から保持期間を数える。保存途中の一時ファイル、ロックファイル、内容が同じ再保存は旧版作成の対象から外す。実装上の判断として、名前変更だけの場合の本体退避は省く。内容と名前を同時に更新するときは更新前の両方を旧版に残す。

現行の[ゴミ箱運用](cloud-trash-retention.md)は、確認済みのゴミ箱移動時刻から720時間が経過した対象を、日次Cronで順次完全削除する。実際の削除時刻は定期実行時刻・処理予算・安全停止の状態による。手動完全削除・ゴミ箱を空にする操作は既存の権限と処理に従う。旧版もこの保持期間と手動操作の対象にする。

更新処理は次の順序で確定する。

1. Windows端末で新しい内容を暗号化し、新しいR2 objectへ送信して保存結果を確認する。
2. 現行file ID・期待した版・親フォルダ・権限・削除状態を再確認する。
3. D1の同一transactionで、更新前の本体・サムネイル・暗号化メタデータ・鍵envelopeを持つ旧版レコードと確認済みのゴミ箱操作を作成し、現行file IDを新版へ切り替える。旧版作成と新版確定の片方だけを成功させない。
4. 操作IDと確定版を記録し、成功応答が失われても同じ更新で旧版が重複作成されないようにする。競合・オンライン削除・権限変更が先行した場合は新版を確定せず、編集内容を保全する。

旧版には独立したゴミ箱内file IDを割り当て、元file ID・元の版・退避操作との対応を保持する。現行file IDは通常保管のままとし、旧版退避を同期上の現行ファイル削除として配信しない。Windowsはゴミ箱内の旧版を全原本の自動取得対象から外し、HDDでは最新版を保持する。

現行の完全削除処理は、別レコードと同じR2キーを共有すると削除を拒否する。旧版と最新版の本体・サムネイル等は独立した参照へ移行するか、同じ安全条件を満たす参照管理を実装してから期限削除へ接続する。最新版や復元済み項目が参照しているobjectを消さない条件を維持する。旧版の暗号化メタデータと鍵envelopeは保存し、期限内の端末復号と復元を可能にする。

ゴミ箱表示には、通常の削除と上書き前の旧版を判別できる情報、元の名前、版の退避日時を付ける。現行の一覧は上限500件のため、旧版増加後も目的の項目を探せるページングが必要となる。旧版の保存量をゴミ箱使用量へ含める。

利用者は、旧版を別名で復元し、現在の最新版も残す方式を選択した。復元した旧版は独立した通常ファイルとして扱い、HDDにも取り込む。復元名には元の拡張子を保持し、同名ファイルがある場合は連番等で衝突を避ける。復元の再試行では操作IDと保存結果を照合して重複作成を防ぐ。復元先フォルダや権限が変わった場合は、現在の認可と鍵の到達性を確認してから処理する。

この処理は現行の単体削除・復元APIの呼び出しだけでは実現できず、旧版の記録・条件付き更新・表示・復元の追加実装が必要となる。

## 削除禁止とエクスプローラーの表示

利用者は、HDDの実際の保存先フォルダから開いた場合も非表示を必須と指定した。CFAPIだけでは標準ファイルの削除属性・メニューは変わらないため、実フォルダのdesktop.iniを接合点とするネイティブShellフォルダ拡張でSFGAO_CANDELETEとdeleteコマンドを制御する。配下のフォルダへのBindToObjectにも同じ制御を引き継ぐ。[MicrosoftのShell属性](https://learn.microsoft.com/en-us/windows/win32/shell/sfgao)、[実フォルダを接合点にする仕様](https://learn.microsoft.com/en-us/windows/win32/shell/nse-junction)。

CFAPIには削除要求への応答で処理を拒否する仕組みがある。これは削除処理の制御に利用する候補であり、メニューの非表示は別に検証する。プレースホルダーでない新規ファイル、プロバイダー停止中、再接続・障害時の動作も検証対象とする。[Microsoftの削除応答仕様](https://learn.microsoft.com/en-us/windows/win32/api/cfapi/ns-cfapi-cf_operation_parameters)。

アプリの上書き保存には元ファイルの削除・改名・置換を伴うものがある。削除権限を一律に拒否すると、利用者が希望する名前変更・上書きも失敗し得る。ユーザーの削除と保存処理を安全に判別できる方式を合成データで確認する。オンライン削除を反映するクライアント自身の操作は、確認済みのfile IDと版に限定して許可する。[Microsoftのファイル置換仕様](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-replacefilew)。

Excelの通常保存は、一時ファイルへの書き込み、元ファイルの削除、一時ファイルの改名を伴うことがMicrosoftから明示されている。Officeの保存操作の完了、保存中の強制終了、Office以外の削除要求を検証し、一律の削除権限拒否によって通常保存を壊さない方式を選ぶ。[MicrosoftのExcel保存手順](https://learn.microsoft.com/en-us/office/troubleshoot/excel/issue-when-save-excel-workbooks?tabs=third-party)。

Shell拡張はC++のネイティブDLLとし、ExplorerへCLRを読み込む方式は採用しない。[Microsoftの指針](https://learn.microsoft.com/en-us/windows/win32/shell/shell-and-managed-code)に従う。管理者による直接操作や別のPCから通常のHDD実体を操作することは、通常利用時の削除防止と区別する。アプリ未導入のPC、アンインストール、外付けの切断時に接合点が原本へのアクセスを妨げない復旧・解除手順は製品化前に検証する。

### 実装したfixtureでの確認結果

OS一時領域の独立したNTFSフォルダを登録し、同じ条件で削除拒否の有無を比較した。別プロセスからの通常削除は拒否された。改名、直接書込、バックアップ先を指定したFile.Replaceは成功した。プロバイダー自身のI/Oだけでは削除通知を検証できないため、PowerShellの独立した子プロセスから実行している。

任意位置の読み取り試験もプロバイダーと別の.NETプロセスへ分離し、末尾・先頭・チャンク境界・全体をハッシュで照合する。TRANSFER_DATAはWindowsの要件に従い、開始位置と転送長を4 KiB境界へ広げ、論理EOFだけを短い最終転送とする。CF_EOFと大きい値でのオーバーフローも回帰対象に含める。失敗時は合成fixtureの処理段階と数値HRESULTを返し、ファイル内容を出力しない。[TRANSFER_DATAの範囲要件](https://learn.microsoft.com/en-us/windows/win32/api/cfapi/ns-cfapi-cf_operation_parameters)。

Excelを非表示の専用インスタンスで起動し、合成.xlsxのCFAPIファイルを編集・保存した。閉じてから読み取り専用で開き直し、セルの更新値を確認した。削除拒否コールバックは保存中にも発生したが、保存と内容確認が成功した。ただし保存後の実ファイルは通常ファイルへ置き換わり、その直後の別プロセスからの削除は成功した。保存成功だけを削除保護との両立の証拠にしない。

保存後のファイルをCfConvertToPlaceholderのALWAYS_FULLで再管理すると、保存内容を保持したまま削除要求を拒否できた。変換時にDEHYDRATEやMARK_IN_SYNCは指定しない。未送信の編集を送信済み扱いにしない。この変換は保存・新規ファイル検出後に必要となり、変換までの空白と常駐停止中の挙動を別途扱う。[変換API](https://learn.microsoft.com/en-us/windows/win32/api/cfapi/nf-cfapi-cfconverttoplaceholder)。

ネイティブShell試作では、通常の保存先パス、新規の通常ファイル、深い配下フォルダのファイルについて、CanDelete=false・deleteコマンドなし・CanRename=trueを別プロセスで確認した。Windows 11の実際のExplorerでも新旧メニューと複数選択で削除が非表示になり、F2による改名が成功し、Delete／Shift+Delete後も対象が残った。上部ツールバーの削除ボタンは非活性で残る。現時点の非表示の指定対象は右クリックメニューであり、ツールバー自体の非表示は達成していない。

初期の管理コードによるCOM試作は独立したテストプロセス内で異常終了したため破棄した。ネイティブ初期試作もExplorerの選択・メニュー検証中にSHELL32.dllでアクセス違反を起こした。試験登録・フォルダは解除し、通常のフォルダ画面へ復旧した。以後は独立したIExplorerBrowser試験プロセスを追加し、IObjectWithSiteの転送を実装して名前変更を確認した後、通常のExplorerで上記の再検証を行った。再検証ではクラッシュは記録されなかったが、全環境での安定性を証明する結果とは扱わない。

Word・PowerPoint、常駐停止中・切断中、検索結果や別アプリからのファイル操作は未検証。一般の通常ファイルに対する全プロセスからの削除をCFAPIだけで禁止できるとは扱わない。ユーザーHDDの登録、既存ファイルの操作、Cloudflareへの接続はこの検証に含めない。

## 構成

`tcloud-windows/src/TCloud.Sync.Core`が暗号化互換、同期判定、転送記録を担当する。`TCloud.Sync.Windows`が保存先検査とCFAPIを担当し、Hostに認証とユーザー操作を接続する。CFAPIは一覧とエクスプローラーへの統合に利用する候補とし、全原本の順次取得を基本動作にする。取得済み本体を常時保持できる設定を検証する。ExplorerのT-Cloud表示を基本とし、T:の割り当ては互換性確認後の追加候補とする。

ファイル本体・Windowsプレースホルダーは選択したNTFSへ、一覧・サムネイルの補助キャッシュと転送記録はPC側のユーザープロファイルへ保存する。外付け側のデータ領域とCookie・PRF・秘密鍵の保管領域を分離する。

CFAPI自体のメタデータもHDDにあるため、HDD休止復帰の待ち時間はなくならない。ウイルス対策等の読み取りが暗黙的取得を起こす場合があり、全アプリの読み取り要求と人間のダブルクリックを同一視しない。ファイル数や媒体別の実測は未実施。

## Windowsの認証と秘密鍵保護

利用者は以下のWindows固有の鍵保管案を、ログインが正常に行え、Cloudflareへ平文のファイル本体・復号鍵を渡さない条件で了承した。AGENTS.md第8・9節と[既存パスキー仕様](security/passkeys.md)に従い、実パスキーの互換性と非抽出キーの保護を検証して採用する。

### 変更しない事項

- 現在のRP ID／origin、招待・管理者承認、Identity／service link／root scope、一般利用と管理者利用の分離。
- 通常のWebパスキーセッションの署名検証、credential・Identity・link・epoch失効照会、現行の12時間rollingと前面・直近60秒の操作条件。Windowsのバックグラウンド処理でこのWebセッションを延長しない。
- 既存のWebAuthn PRF、HKDF、RSA-OAEP SHA-256、AES-GCMとファイルの暗号化形式。既存credential・鍵envelope・ファイルを交換・再暗号化しない。
- PRF出力・秘密鍵・folder key・file keyはサーバー、Git、ログへ送らない。既存PWの公開ログインは復活させない。

### Windowsで追加する事項

1. Windows WebAuthn APIで既存の招待・承認済みパスキーを使う。PRFは現在と同じ入力・コンテキストで評価し、非対応時はログインできたことだけを理由に復号を許可しない。
2. 初回だけ既存のサービス固有パスキーsessionでWindows端末を登録する。初回CookieはWindows DPAPI CurrentUserで保護できるが、永久利用の根拠にはしない。端末登録後の同期はWindows専用の端末認可で行い、通常のWeb sessionの期限を延長・復活させない。
3. PRFで解除した既存RSA秘密鍵はWindows CNGのユーザー用Key Storage Providerへ非抽出設定で取り込み、Windowsの端末登録とIdentity／role／service link／認可範囲／復号用公開鍵指紋に結び付けて保持する。平文PKCS#8のディスク保存やexportable設定へのfallbackは行わない。取り込み時の一時メモリは処理後に消去する。
4. 同期用の端末証明には別の非抽出の署名鍵をWindows CNG内で生成する。Cloudflareへ保存するのは署名検証用公開鍵と認可情報だけとする。秘密鍵・復号鍵・PRF出力をサーバーやHDDへ保存しない。端末の秘密鍵で一回限りの短命challengeに応答し、短命の同期用アクセス権を自動更新する。端末登録自体に定期的な再ログイン期限を設けない。
5. 再起動・再接続時は端末の証明と現在のIdentity／credential／service link／権限・失効状態を確認してからオンライン同期を再開する。短命アクセス権の期限切れは端末の証明で自動更新し、通常の再起動やWebセッションの12時間経過だけでパスキー入力を求めない。端末解除や管理者による失効時は同期を停止し、その端末の認可・保護鍵を破棄する。既にHDDへ保存した平文本体はそのまま残す。
6. folder key・file keyはメモリ内だけで使用する。アプリ終了や失効・認可範囲変更時には該当する一時鍵を消去する。永続CNGキーの削除は対象の端末登録に限定し、他の端末やアカウントのキーを消さない。Webパスキーsessionの期限とWindows端末登録の寿命は混同しない。

この長期端末認可は利用者の「一度認証したらそれ以降は永久的にアクセス」「HDDという物理の特例」「パスキー設計そのものを変更するものではない」という追加指示を具体化するWindows側の特例である。Windows専用API・初回登録helper・登録情報のDPAPI保存・自動証明更新を実装した。まだ公開・実端末登録はしていない。登録は既存の承認済みパスキーから行い、失効確認を省略する無期限Cookieは採用しない。既存ファイルの再暗号化やパスキーの再登録は不要とする。

この変更はWindowsユーザー・PCにオンライン同期用の鍵保護を依存させる。別PCや別のWindowsユーザーが同期を行う場合は、その端末で初回登録を行う。保存済みの平文本体を読むだけなら端末登録もパスキーも不要で、Windowsの通常のファイル権限で扱う。HDDの媒体識別は別媒体への誤書き込み防止に用い、HDD自体にオンライン認証用の秘密情報を持たせない。

### 端末側の実装・検証状況

WindowsPrivateKeyにCNGのユーザー単位の永続RSA取り込みを実装した。秘密鍵のexport policyをNone、用途を復号専用に設定してfinalizeし、再オープン時にも設定を照合する。合成鍵でOAEP-SHA256復号、再オープン、PKCS#8／秘密パラメータの書出し拒否、署名拒否、鍵の削除を確認した。KSPのimportだけでは同じ名前の鍵の置換を防げないケースを検出したため、Windowsアカウント・鍵名に対応するプロセス間mutexと既存キー確認を追加した。既存キーは再取り込みで上書きしない。

WindowsAccountProtectionにDPAPI CurrentUserのCookieバイト保護を実装した。LOCAL_MACHINEは指定せず、用途とsession bindingを追加entropyに含める。合成Cookieで復元、改ざん拒否、別bindingの拒否を確認した。他のWindowsアカウントでの実行は未確認。これらのhelper自身はサーバーsessionを検証・延長しない。

WindowsDeviceKeyにCNGのユーザー単位・非抽出ECDSA P-256署名鍵を追加した。復号用RSA鍵と分離し、サーバーに渡す公開鍵だけを書き出す。固定のWindows端末認可用途・origin・端末ID・challenge ID・nonce・scope hash・短命の有効期限を署名へ含める。合成鍵で再オープン、既存鍵の上書き拒否、秘密鍵の書出し拒否、期限切れ・不正nonceの拒否、WebCryptoによるP1363署名検証と別用途の拒否を確認した。DPAPIの端末登録情報はCookieと用途を分離し、相互に復元できないことを確認した。このhelperだけでは登録の永続化やサーバー側のnonce消費・失効確認を実現したことにはしない。

PasskeyEnvelopeは既存Web版と同じHKDF-SHA256・用途文字列・AES-GCMでPRF envelopeを端末内解除し、CNGへ取り込んだ公開鍵との一致を確認する。既存crypto-vault.jsが生成した管理者／memberの合成envelopeを実際に解除し、用途を入れ替えると失敗することも確認した。秘密鍵・PRFは処理後に消去し、PRFを送信用assertionへ含めない。

管理者用envelopeのpublicKeyJwkは現行Security実装で意図的にnullとして保存される。管理者公開鍵はCloudへのhandoff成功後、同じX-TCloud-SessionでGET /cloud/api/crypto-configから取得し、初期化済み・対応cryptoVersion・RSA形式を確認して使う。memberは引き続きcredential固有のvault内公開鍵を使い、管理者公開鍵を流用しない。公開鍵を取得できない場合や秘密鍵と一致しない場合は処理を中断し、取り込み済みの不一致キーを削除する。初期の診断画面は管理者envelope内に公開鍵があると誤認していたため、実パスキーの署名検証後に失敗した。現行のnullを含む応答形・設定APIの取得・認証エラー・公開鍵不一致を合成fixtureへ追加した。

WindowsPasskeyは既存RP ID／origin、requiredの本人確認、credential別PRF inputを維持するWindows WebAuthn APIの接続を実装した。PRF対応のAPI version 4以上を要求し、認証応答のcredential・RP hash・UP／UVを確認する。署名は既存Security APIで検証した後にだけenvelope解除へ使う。2026-11-18、本人が操作した実機のAPI version 9で管理者認証・既存envelope解除・合成データの復号・秘密鍵の書出し拒否・検証キー削除・Cloud／Securityの検証session終了まで成功した。通常利用モードと別のPRF対応端末の実動作は未確認。

`tests/TCloud.Sync.AuthProbe`に、本人がボタンを押したときだけ現行の認証・handoffを使用する診断画面を追加した。通常利用を既定とし、管理者利用は明示選択する。既存ブラウザのCookieを読み取らず、独立したメモリー内CookieContainerを使用する。端末内で既存envelopeを解除し、合成データで復号と非抽出性を確認してから、このツールが作ったCNGキーを削除し、Cloud／Securityの当該検証sessionをログアウトする。本番ファイルの一覧・本体取得や変更は実行しない。結果ファイルは成功項目・API版・利用区分・例外の種類／数値コード・処理段階・確認時刻だけを記録し、Cookie、token、Identity、credential、PRF、秘密鍵、復号鍵を含めない。

`WindowsDeviceEnrollment`は既存のパスキー認証とhandoff、PRF解除を再利用し、5分以内の初回Web sessionとCNG署名鍵の証明でWindows端末を登録する。端末登録情報はPCのユーザープロファイル内へDPAPIで保存し、HDDへは置かない。署名鍵・データ復号鍵の識別子、端末ID・scope hash・保存先媒体の対応だけを保存し、生のCookieやアクセストークンを保存しない。確定応答の消失に備えて登録情報を先に保存する。初回のCloud／Security Web sessionは終了する。`WindowsDeviceClient`は保存済み情報を再読込し、以降はパスキーを呼ばず端末の署名で15分の同期用アクセス権を取得・更新する。暗号化本体のHTTP Range取得もこの認可へ接続した。

Windows APIは`/cloud/api/windows-sync/`配下に分離する。端末の登録自体に定期的な期限を設けず、一回限り・120秒のnonceを署名して更新する。nonceとアクセストークンはhashだけをDBへ保存し、証明の消費と発行を同じD1 batchで条件付き確定する。各データAPIでIdentity・credential・service link・root scope・global epoch・Cloud version・復号用公開鍵指紋を再確認する。Securityの追加migrationは認可状態変更だけを数える世代表とtriggerを追加し、既存Webの認証処理を変えない。無効化後に再有効化しても以前の端末認可は復活しない。カウンター更新、表示名変更、通常のWebログアウトは端末認可を失効させない。Windowsの許可APIを明示し、Web認証・共有発行・暗号設定・原本削除・ゴミ箱操作へ同期用tokenを流用できないようにする。

端末あたり同時に有効なnonceは8件、同じnonceの署名確認は5回までに制限する。登録・更新・解除と、既知のnonceに対する証明の失敗を共通監査へ残し、Windows端末の認証方式として区別する。Windows端末認可をWebの現在ログイン中sessionへ登録・延長しない。無効Identityの既存整理処理は、追加された世代表・triggerの厳密なDDL照合後も従来の削除条件を維持し、認可のtombstoneだけを残す。

ローカルfixtureでWebログアウト後・1年経過後の自動更新、同じ証明の同時再送の片方だけ成功、nonceの期限・改変・蓄積制限、scope・RSA鍵・認可世代の変更後の拒否、一時障害後の再試行を確認した。WindowsではDPAPI登録情報の再読込と移設・改ざん拒否、CNG署名による自動更新、並行アクセスの更新集約、HTTP認可期限切れの安全な再試行を検査する。

公開時は`WINDOWS_SYNC_ENABLED`を既定のfalseにしたWorkerと、旧・新schemaをともに厳密照合できるバックアップ処理を先行公開する。その後Security `0032_windows_device_authority.sql`、Cloud `0014_windows_device_grants.sql`の追加migrationを適用し、対象Workerと両schemaの確認後にWindows用flagを有効化する。停止時はこのflagだけをfalseへ戻す。既存WebやR2本体を変更・削除するrollbackは不要。製品の初回登録画面・常駐・実HDDのCFAPIと同期処理への統合は継続中であり、診断用の一時キーを運用端末の登録済みキーとして扱わない。利用不能でも平文秘密鍵の保存へ切り替えない。保存済み本体はプロバイダー停止・登録解除後も通常のファイルとして保持する。

### HDD原本の保持

全原本を常時オフライン保存するため、取得前のプレースホルダーにも`CF_PLACEHOLDER_CREATE_FLAG_ALWAYS_FULL`を設定する。取得処理は`CfSetPinState(PINNED)`と`CfHydratePlaceholder(0, CF_EOF)`を使い、pin設定成功だけでは保存完了と判定しない。全体の取得成功を待って完了を記録する。自動脱水・ストリーミングによる本体非保持を許可しない。Microsoftの[ALWAYS_FULLの仕様](https://learn.microsoft.com/en-us/windows/win32/api/cfapi/ne-cfapi-cf_placeholder_create_flags)は一度取得した本体の脱水を禁止し、[pinの仕様](https://learn.microsoft.com/en-us/windows/win32/api/cfapi/ne-cfapi-cf_pin_state)もpin中の脱水を拒否する。

所有する一時フォルダ内の合成原本で、全体のバックグラウンド取得、pin属性、脱水要求の拒否、pin解除後もALWAYS_FULLにより脱水が拒否されることを実機確認した。アプリ接続停止後の独立プロセスによる全原本の読み取り・名前変更・内容の上書き、同期登録解除後も編集内容が残ることを検査する。実際のHDDへの常設登録・実データ転送・再起動を伴う製品の確認はまだ行っていない。

`CloudFilesRootRegistration`は媒体と登録済みroot identity・実ファイルIDを照合して再接続し、別の同期rootや既存ファイル入りの未登録フォルダを採用しない。停止時は登録・本体を維持する。明示的な登録解除でも原本を削除しない。`CloudFilesProvider`はFULL取得、常時保持、削除拒否、同期範囲外へのrename拒否を実装した。ネイティブ通知の識別情報をコピーして別処理で取得し、全体が認証済みの原本から転送する。大容量の準備中は`CfReportProviderProgress`で60秒の取得timeoutを更新し、終了時は処理の停止を待つ。合成暗号データの端末内復号・独立プロセスの読み取り・範囲内rename・範囲外移動と削除の拒否・停止／解除後の本体保持まで実機で確認した。実データのsnapshot・変更feed・アップロード／旧版確定との接続は継続中。

## 同期APIの追加設計

実装済みの読み取り側は、追加migration `0015_windows_sync_catalog.sql`で既存Webを含む書き手の更新を観測する。snapshotの上限と継続cursor、catalog世代を確認し、途中更新は後続feedで取得する。フォルダ移動後は現在の祖先と権限を使い、過去の祖先情報で原本を新たに読ませない。Webの確認済みゴミ箱操作だけを明示的なtombstoneとして返す。失敗した完全削除のtransactionはtombstoneもrollbackする。過去のkeyやmetadataを削除通知に含めない。

原本の最初のHTTP Rangeからcatalogの版を要求し、版と同じSQLで取得した不変のobject keyを読む。後続Rangeも版・ETagを照合する。Windows側は全体を同じHDDの専用stagingへ復号し、全チャンクの認証・全体hash・同期記録の確定後にだけCFAPIへ渡す。準備用と確定用で一時的に原本約2個分の容量が必要になる。保存先不足時は原本を消さず保留する。同期記録はPC側で原子的に保存し、scope・媒体・保存先の実ファイルIDに結び付ける。再snapshotで項目が消えただけでは保存済み原本の記録を捨てない。

Windowsの同期root登録には[`CF_REGISTER_FLAG_DISABLE_ON_DEMAND_POPULATION_ON_ROOT`](https://learn.microsoft.com/en-us/windows/win32/api/cfapi/ne-cfapi-cf_register_flags)を指定する。全namespaceを端末側で保持する設計をWindowsへ明示しないと、未取得一覧の要求待ちにより通常ファイルの変換や配下へのplaceholder作成が`0x800700AA`で失敗することを実機で確認した。flagの追加後は新規ローカル保存・アプリのファイル置換後の変換・配下フォルダへの原本保存が通る。再接続でも所有権と実ファイルIDが一致するrootだけへ同じ登録設定を適用する。共有・招待・パスキー・Webの一覧表示は変更しない。

送信用の安定したコピーは`CfOpenFileWithOplock`と短い参照区間で作る。前面アプリの書き込み・置換でoplockが破られた場合は全コピーを破棄して再試行し、ネットワーク送信中に元ファイルのhandleを保持しない。CFAPIが既に管理する非同期handleを.NETのcompletion portへ再登録せず、独立eventの下位bitでCFAPI側への通知を抑止したWin32読取を使う。kernelのI/O完了までbufferとOVERLAPPEDを保持する。

0015のWindows追加DDLもfingerprintを厳密照合する。現行バックアップregistryのCloud baselineは0012であり、既存0013のゴミ箱保持schemaの捕捉・復元対応をWindows追加DDLの承認だけで暗黙に通さない。0015の本番適用・端末認可の有効化前に、0013を含むdurable-data仕様と復元手順を別途整合させる必要がある。現在は未公開・未適用である。

- ファイル／フォルダの単調な版と変更シーケンスを持つ。更新・移動・論理削除・復元を同じ認可範囲の変更フィードへ記録する。削除済みIDを保持して未送信ファイルとの誤認を防ぐ。
- 一覧から不在なだけで削除しない。初回snapshot完了と変更cursorの整合を検証する。cursor期限切れでは再snapshotし、権限失効や途中失敗を削除へ変換しない。
- 内容更新は別のR2 objectへの暗号化アップロード完了後、期待した版が一致した場合だけ同じfile IDの参照を切り替える。DBとR2を一つのトランザクションとみなさない。
- 競合時は内容を上書きせず別file IDの競合コピーを残す。リトライには操作IDを使い、通信切断で完了応答が失われても重複追加しない。
- 現行multipartは1日以上古い未完了uploadを整理するため、長期間の中断時は保存済みローカル本体から安全に開始し直せるようにする。常に部分再開できるとは扱わない。
- 現行の名前変更APIの期待値照合を再利用しつつ、内容更新を含む単調な版へ対応させる。古いWeb・Android利用者からの変更も同じ版へ記録し、Windowsからの条件付き更新で検出する。
- 名前と内容を同時に確定する更新、途中で失われた成功応答の照会、古い内容版の読み取り、切替前後のobject参照保護が必要。旧objectの整理はバックアップと実行中の転送を参照して行う。
- 旧版退避・現行版の切り替え・ゴミ箱操作の作成を同じ条件付きtransactionで確定する。完全削除のmanifest・共有キー拒否・復元競合の既存保護を回帰対象へ含める。
- 0バイトファイル、同名・大小文字衝突、Windows禁止文字、長いパス、一時ファイルの保存・置換を扱う。オンラインの名前は勝手に変更しない。Windows上の表示名とremote IDの対応を保持する。
- Windowsアプリはオンラインの永久削除APIを実装しない。ゴミ箱の既存Web操作は今回の理由だけで変更しない。

## 公開前の確認

基盤fixtureは実ユーザーのデータを使わない。合成APIによるログイン失効、内容更新、競合、削除・復元、送信中編集、切断／再起動、媒体の取り外しを確認する。Office実アプリの上書き保存、写真・動画の改名、同時の改名と編集、オンライン削除と送信の競合、右クリック削除の非表示、Deleteキーや同期場所の外への移動の拒否、オフライン・常駐停止時の制御を受入試験に含める。旧版の作成失敗時のrollback、応答消失後の再試行、30日前後の期限、完全削除と復元の競合、旧版削除後の最新版の復号、旧版の大量表示も確認する。最後に専用テストデータだけで外付け上のCFAPIと実パスキーを確認する。本番ファイルの削除や大量転送を試験に使わない。

新しいクライアントはまだ公開対象ではない。認証・API・インストーラーが揃うまで、基盤変更を理由にCloud/Security Workerを公開しない。

## 確定事項と残る実装判断

- 右クリック削除は、HDDの実際の保存先から開いても非表示を必須とする。利用者回答で確定済み。
- オンライン削除時の未送信編集は、同期対象外の回復フォルダへ保全する案。同期場所からの削除と編集内容の保全を両立させる。
- 旧版の保存先はT-Cloudオンラインのゴミ箱、保持期間は30日経過後の自動完全削除、復元は別名で戻して最新版も保全する方式で確定した。名前変更だけでの旧版本体作成は省く方針を実装上の判断として採用した。

SyncPlannerはローカル削除からオンライン削除へ進まないよう更新済み。旧転送記録の削除操作も読み込み・保存時に拒否する。全原本取得の判定と古い削除通知を拒否する回帰試験を追加した。これらは判定とfixtureであり、実データへの反映処理はまだ接続していない。
