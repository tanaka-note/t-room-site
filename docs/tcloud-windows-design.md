# T-Cloud Windows同期設計

状態: 2026-10-31、同期基盤実装中。以下の「承認対象」は提案であり未実装。本番同期・ユーザー保存先の登録は未実施。

## 確定した動作

- 保存先は選択可能。外付けHDDはNTFS／固定ディスクとして認識される媒体を初期対象とする。WD Elements 25A2、約2TB、D:は読み取り検査済み。フォーマットはしない。
- 一覧・サムネイルを保持し、本体は開いた対象または右クリックでオフライン保存した対象だけ取得する。取得済み本体を平文で保持し、自動解放しない。バックグラウンドで未指定ファイル全体を取得しない。
- 内容編集、上書き、名前変更、同じ認可範囲内の移動、コピーによる追加アップロードを可能にする。
- ローカル削除はT-Cloudオンラインのゴミ箱へ移す。ファイルID、親フォルダ、暗号化メタデータ、鍵envelope、R2参照を保持し、Windowsから永久削除やゴミ箱全消去APIを呼ばない。
- オンライン削除を他端末にも反映し、自動で再アップロードしない。ファイルが使用中なら反映を保留する。
- オフライン編集と別端末更新が競合したら両方を保全する。削除と未送信編集の競合は、同期場所から外した編集版を回復用に保全する方針案。回復用データは自動アップロードしない。
- HDD未接続・I/O失敗・権限失効・不完全な一覧は削除の証拠にしない。同じドライブ文字の別媒体には処理を継続しない。
- 「空き領域を増やす」はローカル本体の解放だけを扱い、オンラインの論理削除と区別する。
- ExplorerのT-Cloud表示を基本とし、T:の別名表示は互換性確認後の追加候補とする。

## 構成

`tcloud-windows/src/TCloud.Sync.Core`が暗号化互換、同期判定、転送記録を担当する。`TCloud.Sync.Windows`が保存先検査とCFAPIを担当し、Hostに認証とユーザー操作を接続する。CFAPIはPROGRESSIVE取得を使う。取得処理はファイルIDと内容の版に固定し、取得途中で別の版のチャンクを混ぜない。

ファイル本体・Windowsプレースホルダーは選択したNTFSへ、一覧・サムネイルの補助キャッシュと転送記録はPC側のユーザープロファイルへ保存する。後者のキャッシュはアカウント・認可範囲を分離する。外付け側にCookie・PRF・秘密鍵を配置しない。

CFAPI自体のメタデータもHDDにあるため、HDD休止復帰の待ち時間はなくならない。ウイルス対策等の読み取りが暗黙的取得を起こす場合があり、全アプリの読み取り要求と人間のダブルクリックを同一視しない。ファイル数や媒体別の実測は未実施。

## 承認対象: Windowsの認証と秘密鍵保護

AGENTS.md第8・9節と[既存パスキー仕様](security/passkeys.md)に従い、以下のWindows固有の鍵保管を承認後に実装する。既存ブラウザの保管方式をそのままネイティブプロセスへ転用できないため、ファイル本体の平文保存とは別の設計確認が必要。

### 変更しない事項

- 現在のRP ID／origin、招待・管理者承認、Identity／service link／root scope、一般利用と管理者利用の分離。
- 署名検証、credential・Identity・link・epoch失効照会、現行の12時間rollingと前面・直近60秒の操作条件。バックグラウンドpollingだけでは延長しない。
- 既存のWebAuthn PRF、HKDF、RSA-OAEP SHA-256、AES-GCMとファイルの暗号化形式。既存credential・鍵envelope・ファイルを交換・再暗号化しない。
- PRF出力・秘密鍵・folder key・file keyはサーバー、Git、ログへ送らない。既存PWの公開ログインは復活させない。

### Windowsで追加する事項

1. Windows WebAuthn APIで既存の招待・承認済みパスキーを使う。PRFは現在と同じ入力・コンテキストで評価し、非対応時はログインできたことだけを理由に復号を許可しない。
2. 同じサービス固有sessionをWindows専用の保護領域に保持する。CookieはWindows DPAPIのCurrentUserで保護し、LocalAppData内の本人だけがアクセスできる領域に置く。サーバーの期限を延長・復活させる別tokenは発行しない。
3. PRFで解除した既存RSA秘密鍵はWindows CNGのユーザー用Key Storage Providerへ非抽出設定で取り込み、セッションと厳密に結び付ける。平文PKCS#8のディスク保存やexportable設定へのfallbackは行わない。取り込み時の一時メモリは処理後に消去する。
4. 保護キー名はsession／credential／Identity／role／service link／認可範囲／epoch／公開鍵指紋の結び付きを確認する。再起動時は先にサーバーsessionを検証し、同じ結び付きの場合だけ鍵を使用する。ローカル記録だけで期限を延ばさない。
5. folder key・file keyはメモリ内だけで使用する。ログアウト、期限切れ、失効・認可範囲変更が分かった時点で対応するメモリ・Cookie・CNGキーを破棄する。他のsessionのキーを削除しない。
6. CFAPIの要求を起こしたプロセスとWindowsの前面状態・実操作を照合し、現行の前面操作条件に相当する場合だけ活動通知を送る。ファイルの先読み・常駐処理・全フォルダ走査だけでは活動扱いにしない。判断不能時は延長しない。

この変更はWindowsユーザー・PCに鍵保護を依存させる。Windowsユーザー切替やPC移行で保護データをコピーしても再利用させず、パスキーでの再認証へ戻す。ローカル本体はユーザー承認済みの平文なので、既に取得済みの本体はクラウド認証が切れてもWindowsの通常のファイル権限で読める。

この提案の実装前には、CNGの非抽出キー取り込み・削除と実パスキーのPRF互換性を小さなfixtureで確認する。利用不能でもDPAPIで平文秘密鍵を自動保存する代替へ切り替えない。

## 同期APIの追加設計

- ファイル／フォルダの単調な版と変更シーケンスを持つ。更新・移動・論理削除・復元を同じ認可範囲の変更フィードへ記録する。削除済みIDを保持して未送信ファイルとの誤認を防ぐ。
- 一覧から不在なだけで削除しない。初回snapshot完了と変更cursorの整合を検証する。cursor期限切れでは再snapshotし、権限失効や途中失敗を削除へ変換しない。
- 内容更新は別のR2 objectへの暗号化アップロード完了後、期待した版が一致した場合だけ同じfile IDの参照を切り替える。DBとR2を一つのトランザクションとみなさない。
- 競合時は内容を上書きせず別file IDの競合コピーを残す。リトライには操作IDを使い、通信切断で完了応答が失われても重複追加しない。
- 現行multipartは1日以上古い未完了uploadを整理するため、長期間の中断時は保存済みローカル本体から安全に開始し直せるようにする。常に部分再開できるとは扱わない。
- 0バイトファイル、同名・大小文字衝突、Windows禁止文字、長いパス、一時ファイルの保存・置換を扱う。オンラインの名前は勝手に変更しない。Windows上の表示名とremote IDの対応を保持する。
- Windowsアプリはオンラインの永久削除APIを実装しない。ゴミ箱の既存Web操作は今回の理由だけで変更しない。

## 公開前の確認

基盤fixtureは実ユーザーのデータを使わない。認証承認後、合成APIによるログイン失効、内容更新、競合、削除・復元、送信中編集、切断／再起動、媒体の取り外しを確認する。最後に専用テストデータだけで外付け上のCFAPIと実パスキーを確認する。本番ファイルの削除や大量転送を試験に使わない。

新しいクライアントはまだ公開対象ではない。認証・API・インストーラーが揃うまで、基盤変更を理由にCloud/Security Workerを公開しない。
