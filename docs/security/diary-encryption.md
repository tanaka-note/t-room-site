# 日記D1暗号化：実装候補と移行仕様

状態：Draft。手順1（仕様）・手順2（隔離実装と合成データ検証）の成果物。本番接続、実端末の認証、本番データ移行、写真の再アップロード、公開は行わない。

## 対象と保護の境界

目的は、Cloudflare上のDB・バックアップ・APIの保存情報を取得されても、日記の内容を読ませにくくすること。対象は既存データと新規投稿の両方。D1/R2標準の保存時暗号化とは異なり、復号を端末側で行う。

| 情報 | 保存方針 |
| --- | --- |
| 本文、タイトル、タグ、日記の日付、天気、装飾、表示用の著者名・時刻、写真のファイル名・撮影情報・寸法、お気に入り | 暗号化。検索・集計・並び替えは端末内 |
| 世帯・アカウント・記事・写真の不透明なID、公開/下書き/ゴミ箱の区別、保持対象者、関連付け、revision、鍵epoch、同期sequence、操作ID | サーバーの認可、競合制御、参照保護に必要な最小情報として残す |
| パスキーの公開情報、署名済み受取人ディレクトリ、暗号化済み秘密鍵、受取人ごとに包んだデータ鍵 | 保存可能。PRF出力・生の復号鍵は送らない |
| 写真の画像本体・EXIF・既存R2キーやHTTP metadata | 今回の実装で暗号化済みにはならない。後続の写真移行が必要 |
| IP、アクセス時刻、転送量、暗号文サイズ、アクセス頻度・関係性 | 隠せない。ログ最小化は必要だが、この方式で匿名化はできない |

平文のタイトル等をsummaryに残す性能上の例外は採用しない。検索語・タグ名・日付条件も暗号化APIへ送らず、取得済み索引を端末で絞り込む。完全な「メタデータ非公開」を意味しない。

Cloudflareが配信するJavaScriptまで改ざんされた場合、復号後の値やPRFを盗むコードを配信できる。Web版だけでこの攻撃を完全に防ぐことはできない。専用origin、厳しいCSP、外部スクリプト削減、依存・公開経路の検査に加え、より強い保証が必要なら独立した署名配布のネイティブクライアントを検討する。公開コードを読めること自体は復号につながらないが、コード内の脆弱性や認証情報流出は別問題である。

## 暗号と鍵

- AES-256-GCM、ランダムな96 bit IV、128 bitタグを使う。世帯・scope・記事ID・revision・epoch・文書種別・権限関連付けをAADへ結び付ける。
- WebAuthn PRFの32 byte出力から、用途とcredential IDを分離したHKDF-SHA-256でvault用の鍵を導出する。通常のログイン成功だけで復号鍵を発行しない。PRF非対応時にサーバー平文鍵へフォールバックしない。
- credentialごとにRSA-OAEP-3072の受取用鍵とECDSA P-256の署名鍵を分け、秘密鍵はPRFで暗号化する。通常解除した秘密鍵・データ鍵はnon-extractableとしてimportする。ただし同一originの悪意あるコードからの利用を防ぐ保証ではない。
- 公開、共有下書き、個人のお気に入り、保持対象者の組み合わせごとのゴミ箱で鍵scopeを分ける。閲覧者が狭まる操作では、移行先scopeの鍵を持たない操作主でも、正しい受取人へレコード鍵を包んで渡せる。
- 受取人ディレクトリ、権限、公開鍵、epochを管理者のauthorityで署名する。anchorと最低generationは既に信頼する端末またはオフライン復旧物から取得する。同じAPIが返したanchorを初回にそのまま信用してはならない。
- 記事は端末の署名でも検証する。閲覧専用者が公開scopeの復号鍵を持っていても、編集者の署名を偽造することはできない。署名対象は暗号文と認可用metadataの両方である。

コードは標準Web Crypto APIを使うが、独立した暗号・セキュリティレビューは未実施である。

## 現行機能との対応

| 現行機能 | 候補実装・確認範囲 |
| --- | --- |
| 記事作成・編集、装飾、写真マーカー | 既存の入力検証・装飾処理を再利用。暗号化してCAS保存 |
| 検索、タグ、月・日付、お気に入り | 端末内で絞り込み。AND検索・個人別お気に入りを検証 |
| 共有下書き、公開記事からの編集下書き | 編集可能者全員で共有する現行仕様を維持。公開元は公開まで変えず、公開と下書き削除を同一transactionで実行 |
| 通常のuserアカウントでの編集 | role名だけで制限しない。既存のcanManageEntriesに従う |
| 世帯切り替え | 世帯ごとに鍵を分離。全体管理者のお気に入りも世帯ごとに分離 |
| ゴミ箱 | 全体管理者の保持と、本人が自作を削除した場合の個人保持を独立させる。一方の完全削除で他方を消さない。独立世帯の管理者保持と全体管理者の代理閲覧も試験 |
| 同時編集、通信切断後の再送 | revisionによる競合検出。同じ操作IDと同じ暗号文を再送し、異なる内容でのID再利用を拒否 |
| アルバムからの写真削除 | 本文マーカーと装飾のoffsetを調整してmetadataを更新。編集下書きがある場合は競合として停止。参照中の写真を物理削除しない |
| バックアップ・復旧 | 暗号文DBの一貫した読取と空DBへのtransaction復元。元のPRFで実際に復号する試験を実施 |

現行UIそのものをlocalhostのfixtureへ接続し、投稿・詳細表示・お気に入りを確認する。fixtureのfetch差し替えは試験専用であり、本番の接続実装ではない。

以下の本番接続は残っている。従って「既存機能を全て引き継いで公開可能」という判定はまだ出さない。

- Security Centerの実PRF取得、日記向けhandoff、再認証・期限切れ・世帯切替との接続。
- 現行UIへの正式な暗号化adapter。新規写真のstaging・再送・commit・保存用manifest、写真ダウンロード、アルバム全量・検索、各端末の戻る操作の回帰確認。
- Security Centerへの日記復旧envelopeの保存と、既存の管理者復旧操作・承認・監査への正式接続。暗号処理の合成試験と実際のSecurity Center経由の復旧試験は別である。
- 写真upload時に、ファイル名・撮影日時等を既存のFormDataやR2 HTTP metadataへ平文で送らない経路。画像のEXIF自体は後続移行まで残る。
- `/diary/tag/タグ名/`、検索条件や戻り位置のsessionStorage・history、Service Worker/cache、旧画面の残留平文の対処。URLには不透明なIDを使い、保存する状態は暗号化する。
- サーバー時刻の取得・投稿との接続。候補は表示用時刻も暗号化するため、サーバーが暗号文中の時刻を検査する現行と同一の保証はできない。通常UIはサーバー発行時刻を使用する。
- 写真の物理削除queueの正式なdrain。候補は孤立したIDをtransactionでqueueへ登録するだけで、R2へは接続しない。

## 復旧・失効

利用者が保管する日記独自の復旧キーは発行しない。Security Centerにある第一管理者PWによるT-Cloud鍵復旧を利用し、体調管理と同様に既存の復旧基盤へ統合する。日記のscope鍵・署名authorityはサービス専用に生成し、T-Cloudのデータ鍵を日記暗号化へ使い回さない。

信頼端末で日記の復旧kitを独立したランダムAES鍵で暗号化し、そのAES鍵だけを既存のT-Cloud復旧用RSA公開鍵へラップする。サーバーに保存するのは暗号文とラップ済み鍵だけである。復旧用公開鍵のfingerprintも信頼済み端末で照合し、同じAPIから受け取った公開鍵をそのまま信用しない。既存の管理者パスワードやT-Cloud鍵の保存方式・復旧経路は変更しない。

ゴミ箱の保持対象を狭める際などに作る個別レコード鍵にも、署名済みdirectoryにある共通復旧用公開鍵へのラップを必須とする。これがないとscope鍵のkitだけでは一部の記事を復旧できない。通常閲覧ではこの復旧用ラップを使わず、共通の管理者復旧権限を持つ端末内だけで解除する。

全体のkitは全世帯を復旧できるため、復旧権限は全体管理者に限定する。統合すると共通の復旧経路を失った際の影響も共通になる。独立したオフラインキーは別経路を持つ利点があるが、保管負担が増えるため今回採用しない。既存復旧情報と承認済み予備パスキーの保管を維持する。

合成試験では、既存の共通復旧用RSA鍵を使用し、旧パスキーのPRFを使わずkitを開き、新しく承認したcredentialにgrantを発行して、既存の暗号文を復号する。復旧操作中だけ鍵の再ラップに必要なexportを許可し、通常ログインでは許可しない。更新したdirectoryに合わせて復旧envelopeも再作成できることを試験する。JavaScriptの文字列やGC対象を確実にゼロ化することは保証できない。

| リスク | 回避・緩和方法 |
| --- | --- |
| パスキーと既存の共通復旧情報を全て失う | 承認済みの予備パスキー、既存の管理者復旧情報の安全な保管、事前の実復号試験。通常の日記ログイン成功だけでは復号できない |
| 共通の復旧情報の流出 | 復旧権限を限定し、既存の本人確認・再認証・監査を維持。復旧用秘密鍵まで漏えいした場合は日記を含めてscope鍵・authorityの交換が必要 |
| 新規パスキーへの不正な鍵配布 | 既存の招待・承認に加えて、信頼端末で公開鍵fingerprintを照合し署名する。APIの承認フラグだけを信用しない |
| アカウント失効後も取得済み鍵で読める | 失効時は新epochへ再暗号化し、残る閲覧者だけに鍵を渡す。旧暗号文・既取得の平文を取り戻すことはできない |
| 古い正当なDBやdirectoryの再送 | 最低generation・端末で保持したsequence/revisionの検証。候補は開いているセッションで検出。再起動をまたぐtrusted checkpoint保存は本番接続の必須条件 |
| サーバーによる削除・隠蔽・停止 | 暗号化だけでは防げない。別系統のバックアップと、端末が署名する全件manifest/checkpointを組み合わせる |
| DB復元の誤操作 | 空の隔離DBだけへ復元し、署名とAAD関連付け、件数、実復号を検証してから切り替える |

候補の通常clientは現在epochの鍵だけを扱う。パスキー追加時にも個別レコード鍵の受取人更新と旧署名の検証情報の保持が必要であり、directoryの差し替えだけで全データを引き継げるとは扱わない。失効時の全件再暗号化、複数epochの移行期間、更新済み復旧envelopeの保存・検証を終えるまで本番の鍵交換機能として有効にしない。

バックアップのSHA-256は事故による破損検出であり、攻撃者に対する全体の署名ではない。各記事の署名・metadata関連付けは検証するが、攻撃者による全体の間引きや古い一式への巻き戻しには、別に保持した署名済みmanifestと最低checkpointが必要である。

## 既存データの移行手順（後続作業）

1. 専用のHTTPS originと信頼anchorの受渡しを準備する。同じhostの別pathでは、他サービスのJavaScriptからIndexedDBや鍵へアクセスできる境界を分離できない。
2. 実端末でPRF・予備パスキー・既存Security Center経由の復旧を確認する。未保存編集・upload中の自動更新を延期する現行仕様も維持する。
3. 一時的に更新を停止し、本文・下書き・ゴミ箱の保持単位・お気に入り・写真metadataの一貫した読取とmanifestを信頼端末に取得する。移行用の平文dumpをGitやCodex環境へ置かない。
4. 各scopeを読める正当な利用者の端末で、新しい隔離領域へ暗号化保存する。個人専用の保持分は、権限を広げて全体管理者に読ませる方法で集約しない。欠落、重複、参照、競合を検出したら停止する。
5. 全件の復号結果を元データと比較する。候補のimportは元の文字列・null・装飾・写真metadata等を正規化せず保存し、ID・著者・revisionを信頼済み移行台帳と照合する。25件ごとのcheckpointで再開可能とする。移行先の暗号文件数が一致するだけでは検証完了としない。
6. 別の端末・隔離DBでバックアップを復元し、実際に復号・検索・写真参照まで確認してから読取先・新規書込先を切り替える。旧クライアントからの平文書込を止め、旧APIを閉じる。
7. 合意した検証期間後に、移行対象の平文だけを除去する。D1全体を削除しない。認証情報や他機能のテーブルを巻き込まない。
8. 日次・月次・旧世代のバックアップ、D1 Time Travel、ブラウザcache、ログの保持期間も追跡する。元の平文は暗号化列を追加しただけでは消えず、削除直後も過去のbackup/Time Travelには残り得る。写真本体は別工程で移行する。

移行前の旧平文へのrollbackは、新規投稿分の取扱いを決めずに実行してはならない。切替後は原則として暗号化バックアップへの復旧を使う。暗号化済みデータの問題を隠すために自動で平文へ戻す処理は設けない。

## 速度と上限

端末内索引で検索・タグ・月別移動のたびに復号・通信しない。同期はsequenceが同じなら記事転送を省き、変更時は変更されたレコードと削除・権限変更による除外IDだけを同期する。検証済みの同一暗号文を再利用する。初回は最大50件ずつ取得し、途中更新があれば全体を再取得する（最大3回）。5,000レコード・50 MBを越えた場合は停止し、分割索引を設計してから拡張する。

移行では1件ごとの全量再読込を行わない。写真IDの参照保護やrevision競合を同一transactionで処理する。大規模export/backupはD1の応答・実行上限に収まる分割と固定snapshot方式が必要であり、候補の小規模一括backupをそのまま大容量の本番cronへ接続しない。

合成試験は実端末のPRF・回線・描画性能を保証しない。本番切替の合格条件は、現在の端末で同じ操作・同じデータ量を比較し、初回解除、一覧、詳細、検索、写真一覧、長文編集の待ち時間が許容範囲にあること。普段の検索・絞り込みは操作追加遅延100 ms以内、初回の暗号処理増分はPCで1秒以内を暫定目標とし、モバイルは実測後に判断する。速度のために平文をサーバーへ戻さない。

2026-11-11の隔離Chromiumで、合成1,200件・写真metadata 21,600件を追加して測定した結果は次のとおり。PRF待ち・実際の写真画像・画面描画は計測に含まない。p95は記載した有限サンプルの観測値である。

| 測定 | 結果 |
| --- | --- |
| 初回のlocalhost HTTP＋索引処理 | 約1,174 ms（1回） |
| 暗号文検証・復号・索引処理のみ | 中央値387 ms、p95 428 ms（7回） |
| 端末内AND検索 | 中央値0.7 ms、p95 3.8 ms（21回） |
| 変更無しのHTTP同期 | 中央値4.9 ms、p95 11.9 ms（7回） |
| 写真18件のmetadataを含む1記事の編集 | 約28 ms（localhost、1回）。差分1件・約14.4 KB |

初回の暗号文索引はこのfixtureで約17 MBになる。CPU目標だけを満たしても、低速回線での快適さは保証できない。正式接続では暗号文cacheの利用と、本文用索引・写真metadataの遅延取得/分割を検討し、初回転送・画面表示の実測が合格するまで本番切替しない。現在のcandidateの全量初回取得を、そのまま現行同等と判定してはならない。

## Cloudflareの費用

このDraftの検証はローカルだけで、本番のD1/R2/Workersや他サービスの利用量を増やさない。新しい有料リソースも作成しない。

本番移行では日記だけでなく、同じアカウントの他サービスとの合算で次を確認する。契約・料金は適用時に再確認する。

| 利用枠 | 増加要因と制御 |
| --- | --- |
| D1容量 | 暗号文のbase64、署名、二重保持、変更履歴・再送receipt。本文だけでなく全写真metadataを含めて見積もる |
| D1 reads/writes | 初回索引、移行・検証、各更新のtransaction。ページ取得・変更無し応答・移行checkpointで抑制。長期の履歴/receipt清掃も必要 |
| Workers requests/CPU | ページ・鍵metadata・移行リクエスト。AES/RSAの復号は端末側で行うが、署名検証・認可・DB処理のCPUは残る。実際のWorkers CPUは今回未計測 |
| R2容量・Class A/B | 暗号化backup、新旧世代の重複、backup書込・復元読取。他サービスが既に無料枠を使っていれば増分は従量料金になる |
| その他 | logs、Queues、Cron、他サービスへのbackup転送、外部保管先。今回新たなQueueや有料originは用意しない |

例として、追加D1を100 MB以内、暗号化backupを1世代100 MB以内×42世代に制限した場合、R2 Standard $0.015/GB-monthとD1追加storage $0.75/GB-monthでは保存分の上限目安は約$0.14/月（D1が契約内なら約$0.063/月）。これは保存分だけの保守的な計算で、全体料金の保証ではない。各実行・操作課金は別である。画像本体の再アップロード・世代重複は今回の範囲に含めず、写真移行時に別途算定する。

使用量の枠を日記専用の独立枠と見なさず、他サービスの増加分も加えて月末予測する。移行バッチ量とbackup世代数に上限を設け、請求通知と実測を確認する。Cloudflareの通知は課金の強制停止機能ではない。

参考：[D1 pricing](https://developers.cloudflare.com/d1/platform/pricing/)、[D1 limits](https://developers.cloudflare.com/d1/platform/limits/)、[Time Travel](https://developers.cloudflare.com/d1/reference/time-travel/)、[Workers pricing](https://developers.cloudflare.com/workers/platform/pricing/)、[R2 pricing](https://developers.cloudflare.com/r2/pricing/)、[WebAuthn PRF](https://www.w3.org/TR/webauthn-3/#prf-extension)。

- `diary-worker/e2ee/`：暗号・鍵解除・復旧・認可・暗号文保存・移行・backup・IndexedDB候補。
