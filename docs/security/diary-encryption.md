# 日記D1暗号化：実装候補と移行仕様

## 2026-11-12に確認した実装計画

- 家計簿と同じく、既存の承認済みパスキーのPRFで端末内のサービス専用鍵を解除する。パスキー秘密鍵を日記のデータ鍵として直接使わず、PRF・平文の秘密鍵・復号鍵をサーバーへ渡さない。
- 復旧の入口はSecurity Centerへ統一する。既存T-Cloud管理者復旧基盤のRSA鍵で日記専用の復旧bundleを保護し、利用者が別途保管する日記独自の復旧キーは発行しない。日記のscope鍵・署名authorityは他サービスのデータ鍵と分離する。
- 第1段階はD1の本文・タイトル・タグ・日付・写真metadata等の暗号化と、その新規投稿・既存データ・バックアップの復旧検証。既存パスキーの追加／失効、複数account／世帯、既存Security Center経由の復旧を同じ境界で確認する。
- 第2段階は大量の写真本体のゼロ知識暗号化。原本・表示用・サムネイル・EXIFを含めて保護し、Cloudflare側で復号する方式にしない。現在の写真は第1段階で暗号化済みと表示せず、既存R2 objectの再アップロードや削除を先行しない。
- 写真表示の速さも受入条件とする。暗号化サムネイル／表示用画像の可視範囲取得、暗号文cacheの再利用、必要な分だけの端末復号と先読みを検討し、初回・再訪・スクロール・写真切替の表示時間、転送byte、メモリ、端末負荷を現行と比較する。全原本の一括取得／復号で一覧を待たせず、鍵の期限・失効・account／世帯境界を性能のために弱めない。具体方式と許容値は合成データと実端末の測定後に確定する。

## D1先行移行の承認と現在の状態（2026-11-15）

利用者はD1の既存データと今後の全利用者の投稿を暗号化へ移行する方針、および第一管理者の既存中央復旧による全件鍵更新を承認した。本文・お気に入り等の通常編集権限は変更しない。`canManageEntries`のある利用者はrole名にかかわらず暗号化投稿でき、未準備のパスキー／非対応PRFでは平文へフォールバックしない。写真本体・EXIF・R2 HTTP metadataの暗号化と再アップロードは後続工程である。投資履歴も利用者が今回の暗号化対象へ追加することを承認した。従来のcanViewInvestmentによる閲覧範囲を維持し、通常の更新署名は第一管理者のサービスaccountへ限定する。

実装は #227・#230 から本番公開済み。検証済みmain `ea90fa073c76a96629643a7c1fb903ddc0ccebc8` からBackup Workerを先に公開し、本番schemaを追加した。専用origin `https://diary.tanaka-note.com` は既存Diary WorkerのCustom Domainとして準備済み。この設定では鍵の利用準備APIを公開するが、D1のrolloutは`legacy`・generation 0のまま維持し、投稿停止・既存データ移行・平文削除は行わない。実端末でのPRF／第一管理者PW復旧、本番データ移行はまだ実施していない。過去のバックアップ／Time Travelも平文化したまま残り得るため、この段階を完全移行済みと報告しない。

- #155・#128・#132・#229を含むmainを取り込んだ。写真コピー用Cronを再開せず、正式写真の既存R2 objectを再保存・削除しない。
- 初回移行は旧DBの書込fenceを確認し、固定sourceを管理者端末で暗号化する。本文・著者・revision・下書き・保持範囲・写真順・個人のお気に入り・投資履歴を引き継ぐ。旧DBのタイトル等の原値も暗号文内へ保管し、入力の再正規化で失わない。
- 全件鍵更新は端末で旧署名・復号結果と新しい復号結果を照合し、authorityによる復旧専用attestationを付ける。公開証明は旧暗号文のdigest・世代・新暗号文を結び付ける。平文一致は管理者端末が検査・証明するもので、第三者が平文を見ずに一致を数学的に検証するゼロ知識証明ではない。通常編集APIは引き続き本人の署名と権限を要求する。
- 暗号化済み移行planだけを端末のIndexedDBへdurable保存し、同じ暗号文で中断再開する。成功済みbatchの件数とplan digestを小さな別checkpointへ保存し、再認証後に完了済み全件を再送しない。写真metadataは既存R2参照を維持してD1内で暗号化する。全件更新は小分けstagingと署名済み全体digestで照合し、全件が揃ってからatomicに適用する。
- 復元確認ファイルは隔離SQLiteへ実際に復元した暗号文から作る。管理者端末が全記事・summary・写真metadataを再復号し、plan・現DB・復元DBの全件一致を確認して切替evidenceへ署名する。初回の最終切替では旧D1本文・タグ・写真metadata・お気に入り・投資履歴等の削除と暗号化投稿の有効化を同じtransactionに含める。失敗時は元の平文と投稿停止状態を維持する。
- 日記用v10 exportは旧平文の日記tableを含めず、暗号文と同世代の署名済みdirectory・PRF封印vault・scope grants・追加record grants・中央復旧envelopeを同梱する。Securityはv4へ鍵tableも保存する。固定D1 exportを分割し、鍵世代が変われば公開を拒否して直前の正常世代を残す。移行／鍵更新の復元確認には同日の日次を上書きしない専用checkpointを作る。
- 空の隔離DBへの復元はpausedのままとし、バックアップ内のアカウント／認証情報も従来どおり隔離する。元のパスキーと追加grantsによる再復号を試験する。既存の写真backup方式とスケジュールは維持する。

### パスキー利用と鍵管理の統一（2026-11-16）

Security Centerは初期登録・招待・承認・連携・失効・復旧の入口とする。通常の利用者はT-Cloud／家計簿と同じ登録済みパスキーで日記へログインし、端末内で日記専用vaultと信頼設定を自動準備・解除する。公開JSONの保存・読み込みや、日記専用の鍵承認画面は通常利用の条件にしない。登録済みの鍵・管理者復旧envelopeを引き継ぎ、パスキーを再登録しない。

初回の信頼設定は、Security Centerの本人認証済み応答／対象サービスhandoffから確立する。これは既存T-Cloudと同じくSecurity Centerの認証・初期配布を信頼する境界であり、サーバーから独立した外部ファイルで初期anchorを照合する方式ではない。Diary profileの公開anchorからは初期化しない。受け取った公開anchorと最小generationを、本人のPRFから用途分離したAES-GCM鍵で暗号化し、recipient ID・generationへ結び付けて既存vault行へ保存する。サーバーにはPRFも生の復号鍵も渡さない。以後は同じパスキーで封印済み設定を開き、端末内の既知anchor・generationと照合する。破損・別credential・別recipient・anchor変更・巻き戻しでは初期配布へfallbackしない。専用originや別端末でもファイルを引き継がず同じ経路を使う。

通常の管理者ログインは、既存の承認済みIdentity／credential／日記連携・scopeに限って準備済み利用者へ鍵を委譲する。初期化と新規委譲が必要なときだけ、既存T-Cloud管理者PRF envelopeを端末内で解除する。グローバル復旧鍵を利用できる自動管理経路は第一管理者Identityかつ日記のglobal ownerアカウントに限定し、一般利用用アカウントには合成しない。通常ログインごとにgenerationを増やさない。新しい受取人には完全な暗号文台帳から個別レコード鍵も再ラップする。失効・権限縮小では自動的に旧鍵を再配布せず、全件鍵更新を要求する。

vault／封印済み信頼設定の登録は5分以内の本人認証を要求する。Diaryは署名済みサービスsessionを確認し、SecurityはIdentity・credential・連携・epoch・accountを再確認する。封印済み設定はgenerationのCASで更新し、応答喪失・同時実行では保存済み設定を再解除して一致を確認する。通常の端末pinは公開鍵のSHA-256指紋と最小generationだけを保持し、再試行用の設定全体も本人のPRFとrecipientへ結び付けて暗号化する。設定保存前の通信失敗でも同じ暗号化済みproposalから再開する。vaultの公開鍵・署名鍵・privateEnvelopeは置換しない。一般利用者の初回準備後、管理者の次の通常利用までは鍵委譲待ちになることがある。暗号化後は未準備・PRF非対応でも平文へ戻さない。

同じ有効なサービスsessionでは、端末のIndexedDBに保持した非抽出・decrypt専用RSA鍵と非抽出・sign専用署名鍵から再開する。bindingはsession ID・Identity・credential・link・account・version・epoch・directory generation・公開鍵を含む。毎回live sessionを照合し、署名・grantsの実解除でも鍵を検証する。期限・ログアウト・session切替・失効を越えて利用せず、端末内の生PRF／生scope鍵／平文データは永続化しない。対応しない保存環境は通常パスキーログインへ戻す。

初回の全件移行と全件鍵更新は管理者の初期・保守操作とし、全員の準備を確認するまで投稿を停止しない。移行開始後は端末の暗号化planを保存して中断再開し、実際のv10 checkpointを取得する。端末内の新しいSQLite（sql.js 1.16.0）へGit由来のDDLで復元し、全partのSHA-256・schema・件数・各cell・integrity／foreign keysを検証する。復元された暗号文の全件比較・再復号後に既存の切替証明へ署名する。archive内のSQLは実行しない。公開trustや復元確認レポートのダウンロード／手動読み込みは不要である。checkpoint APIは現在の固定台帳に対応するmanifestとそのpart番号だけを公開し、任意R2キーや写真を読めない。

利用設定の予期しない失敗は秘密情報を含まないDKEY段階コードで表示する。実HTTP／session／Originを通した合成ブラウザ試験は、別端末・応答喪失・session再開・失効拒否・実SQLite復元から切替、および旧管理者credentialを失効して新しい管理者credentialへ中央復旧する全件鍵更新までを確認する。仮想Authenticatorによる実WebAuthn PRF／SimpleWebAuthn検証も行うが、利用者の実機／本番移行を代替しない。

### 専用originの運用

Custom DomainはCloudflareのWorkers Domains APIで別管理する。通常のActions公開は既存の`versions upload`／`versions deploy`であり、domain・DNS・既存routeを変更しない。インフラ用の手動公開時は`diary.tanaka-note.com`のCustom Domainと従来の`tanaka-note.com/diary*` routeの両方を維持し、未指定domainの削除を承認しない。不要になった準備用domainのrollbackは、専用originへの切替・暗号化データ移行を開始していないことを確認してから、今回追加したdomainだけを外す。

本番の内容を取得せずに件数・保存byteを確認した時点で、移行元は日記1,235件・写真metadata 21,845件・投資履歴1,523件を含む約20.4 MB。source上限50 MB以内であった。この数値は移行時の固定台帳ではなく、移行開始時には停止済みsourceを改めて照合する。

### 管理者端末と本番の残条件

1. Backup Worker、Security、Diaryを検証した同一commitから準備公開する。候補SQLは通常migrationの外に置いたままとし、適用前にschema・対象DB・既存バックアップを照合する。`node --use-env-proxy tools/prepare-diary-encryption.mjs --infrastructure`は、既存のクラウド環境Network secretを使い、同じmain commitのCI成功と最新main・対象account/DB・既存DDLを確認してBackup Workerを先に公開し、追加schemaだけを適用する。通常のproduction tokenへD1/R2権限を追加しない。投稿停止・暗号化の有効化・平文削除は実行しない。専用HTTPS originと、そのoriginからの日記専用WebAuthn認証を準備する。
2. 第一管理者と各利用者は日記の通常パスキーログインで鍵を自動準備する。管理者は準備済みの鍵を承認し、実PRF、予備パスキー、既存の第一管理者PWからの中央復旧を実端末で確認する。合成PRFやテスト用復旧RSA鍵で代替したとは扱わない。
3. 第一管理者の初期移行操作で「日記の暗号化移行を準備・再開」を実行する。全員の準備確認後に投稿を停止し、暗号化plan・全件import・実checkpointの作成・端末内の隔離SQLite復元・全件再復号・切替証明を一連で実行する。通信が切れた場合は同じ端末から再開する。ファイルの保管・受け渡しはしない。
4. `backup-worker/tools/restore-isolated.mjs`のNode版はオフライン監査用として残す。通常の切替では上記の端末内SQLite復元を使う。
5. 実端末で通常編集者／一般roleの投稿、世帯境界、下書き、検索、お気に入り、写真表示・保存、別端末・再ログインを確認する。
6. 過去のv2〜v9・旧月次backupとD1 Time Travelの平文履歴を棚卸しし、暗号化移し替え・検証・削除または保持期限を記録する。この実装の切替transactionはそれらを削除しない。画像本体も未暗号化であり、「全保管データのゼロ知識化完了」とは区別する。

端末側のsource上限は50 MB、暗号化plan／復元確認ファイルは100 MB。現行snapshotの上限は5,000レコード、全件更新mediaの上限は100,000件。1回の転送は20件または1.8 MB以下。D1の1行へ保存する鍵設定と署名manifestの合計も1.8 MB以下。大容量manifestは件数と全体digestで表し、写真全件のhash一覧をD1の1行へ格納しない。実データが上限を超える場合は上限を黙って緩めず、移行単位を設計・検証する。

### 投資履歴の表示・更新

投資履歴は世帯の共通データと別scopeで暗号化する。従来どおりcanViewInvestmentを持つaccountへだけgrantを発行し、通常の更新は第一管理者の署名・既存のSecurity管理者再認証を必須にする。一般の編集者が閲覧用AES鍵と自分の署名鍵を持っていても、投資履歴の更新署名を偽造できない。

投資画面は同じaccountのパスキーで解除し、1件の暗号化履歴だけを取得・端末内で復号して既存グラフへ渡す。初回画面表示のために全日記・写真情報を読み込まない。金額や日付をURL・history・localStorageへ保存せず、cacheと再開情報はciphertextだけとする。切替後は旧`/api/investment-history`の平文APIと旧D1への直接書込を拒否する。

履歴の追加は既存CSV処理に`--json-output <手元のファイル>`を指定し、Security Centerの第一管理者画面で投資履歴ファイルを選ぶ。JSON/CSVは元データとして本人の端末で扱い、サーバーへは署名済み暗号文だけを送る。通常の本人用PRF vault/grantを使い、投資更新のために他人の個人データ用の中央復旧鍵を開かない。更新のciphertext proposalをdurable保存して応答喪失時に同じ操作を再送する。

投資recordに対応するreader protocolは2とし、切替証明・status・互換rollbackで確認する。暗号化envelopeの保存形式1/2だけに対応する旧readerを、投資履歴へ切替後のrollback先として受け入れない。

## 対象と保護の境界

目的は、Cloudflare上のDB・バックアップ・APIの保存情報を取得されても、日記の内容を読ませにくくすること。対象は既存データと新規投稿の両方。D1/R2標準の保存時暗号化とは異なり、復号を端末側で行う。

| 情報 | 保存方針 |
| --- | --- |
| 本文、タイトル、タグ、日記の日付、天気、装飾、表示用の著者名・時刻、写真のファイル名・撮影情報・寸法、お気に入り、投資履歴の日付・残高・内訳 | 暗号化。検索・集計・並び替えは端末内 |
| 世帯・アカウント・記事・写真の不透明なID、公開/下書き/ゴミ箱の区別、保持対象者、関連付け、revision、鍵epoch、同期sequence、操作ID | サーバーの認可、競合制御、参照保護に必要な最小情報として残す |
| パスキーの公開情報、署名済み受取人ディレクトリ、暗号化済み秘密鍵、受取人ごとに包んだデータ鍵 | 保存可能。PRF出力・生の復号鍵は送らない |
| 写真の画像本体・EXIF・既存R2キーやHTTP metadata | 今回の実装で暗号化済みにはならない。後続の写真移行が必要 |
| IP、アクセス時刻、転送量、暗号文サイズ、アクセス頻度・関係性 | 隠せない。ログ最小化は必要だが、この方式で匿名化はできない |

平文のタイトル等をsummaryに残す性能上の例外は採用しない。検索語・タグ名・日付条件も暗号化APIへ送らず、取得済み索引を端末で絞り込む。完全な「メタデータ非公開」を意味しない。

Cloudflareが配信するJavaScriptまで改ざんされた場合、復号後の値やPRFを盗むコードを配信できる。Web版だけでこの攻撃を完全に防ぐことはできない。専用origin、厳しいCSP、外部スクリプト削減、依存・公開経路の検査に加え、より強い保証が必要なら独立した署名配布のネイティブクライアントを検討する。公開コードを読めること自体は復号につながらないが、コード内の脆弱性や認証情報流出は別問題である。

## 暗号と鍵

- AES-256-GCM、ランダムな96 bit IV、128 bitタグを使う。世帯・scope・記事ID・revision・epoch・文書種別・権限関連付けをAADへ結び付ける。
- WebAuthn PRFの32 byte出力から、用途とcredential IDを分離したHKDF-SHA-256でvault用の鍵を導出する。通常のログイン成功だけで復号鍵を発行しない。PRF非対応時にサーバー平文鍵へフォールバックしない。
- credentialごとにRSA-OAEP-3072の受取用鍵とECDSA P-256の署名鍵を分け、秘密鍵はPRFで暗号化する。通常解除した秘密鍵・データ鍵はnon-extractableとしてimportする。ただし同一originの悪意あるコードからの利用を防ぐ保証ではない。
- 公開、共有下書き、個人のお気に入り、保持対象者の組み合わせごとのゴミ箱で鍵scopeを分ける。閲覧者が狭まる操作では、移行先scopeの鍵を持たない操作主でも、正しい受取人へレコード鍵を包んで渡せる。
- 受取人ディレクトリ、権限、公開鍵、epochを管理者のauthorityで署名する。anchorと最低generationは既に信頼する端末またはオフライン復旧物から取得する。同じAPIが返したanchorを初回にそのまま信用してはならない。
- 記事は端末の署名でも検証する。閲覧専用者が公開scopeの復号鍵を持っていても、編集者の署名を偽造することはできない。署名対象は暗号文と認可用metadataの両方である。

コードは標準Web Crypto APIを使うが、独立した暗号・セキュリティレビューは未実施である。

| 現行機能 | 候補実装・確認範囲 |
| --- | --- |
| 記事作成・編集、装飾、写真マーカー | 既存の入力検証・装飾処理を再利用。暗号化してCAS保存 |
| 検索、タグ、月・日付、お気に入り | 端末内で絞り込み。AND検索・個人別お気に入りを検証 |
| 共有下書き、公開記事からの編集下書き | 編集可能者全員で共有する現行仕様を維持。公開元は公開まで変えず、公開と下書き削除を同一transactionで実行 |
| 通常のuserアカウントでの編集 | role名だけで制限しない。既存のcanManageEntriesに従う |
| 世帯切り替え | 世帯ごとに鍵を分離。全体管理者のお気に入りも世帯ごとに分離 |
| ゴミ箱 | 全体管理者の保持と、本人が自作を削除した場合の個人保持を独立させる。一方の完全削除で他方を消さない。独立世帯の管理者保持と全体管理者の代理閲覧も試験 |
| 同時編集、通信切断後の再送 | revisionによる競合検出。同じ操作IDと同じ暗号文を再送し、異なる内容でのID再利用を拒否 |
| アルバムからの写真削除 | 本文マーカーと装飾のoffsetを調整してmetadataを更新。編集下書きがある場合は競合として停止。参照中の写真を物理削除しない |
| バックアップ・復旧 | 暗号文DBの一貫した読取と空DBへのtransaction復元。元のPRFで実際に復号する試験を実施 |

現行UIそのものをlocalhostのfixtureへ接続し、投稿・詳細表示・お気に入りを確認する。fixtureのfetch差し替えは試験専用であり、本番の接続実装ではない。

回収版にはWorker・公開adapter・Security Centerの接続候補も含むが、以下は本番切替前の未通過条件である。「既存機能を全て引き継いで公開可能」という判定はまだ出さない。

- Security Centerの実PRF取得、日記向けhandoff、再認証・期限切れ・世帯切替との接続。
- 現行UIへの正式な暗号化adapter。新規写真のstaging・再送・commit・保存用manifest、写真ダウンロード、アルバム全量・検索、各端末の戻る操作の回帰確認。
- Security Centerへの日記復旧envelope保存・既存T-Cloud PRF envelope解除の接続候補は隔離試験する。既存の第一管理者PW復旧からの実端末での一連の操作、招待・承認・監査の確認は別の公開条件である。
- 写真upload時に、ファイル名・撮影日時等を既存のFormDataやR2 HTTP metadataへ平文で送らない経路。画像のEXIF自体は後続移行まで残る。
- `/diary/tag/タグ名/`、検索条件や戻り位置のsessionStorage・history、Service Worker/cache、旧画面の残留平文の対処。URLには不透明なIDを使い、保存する状態は暗号化する。
- サーバー時刻の取得・投稿との接続。候補は表示用時刻も暗号化するため、サーバーが暗号文中の時刻を検査する現行と同一の保証はできない。通常UIはサーバー発行時刻を使用する。
- 写真の物理削除queueの正式なdrain。候補は孤立したIDをtransactionでqueueへ登録するだけで、R2へは接続しない。

## 復旧・失効

利用者が保管する日記独自の復旧キーは発行しない。Security Centerにある第一管理者PWによるT-Cloud鍵復旧を利用し、家計簿と同様に既存の復旧基盤へ統合する。日記のscope鍵・署名authorityはサービス専用に生成し、T-Cloudのデータ鍵を日記暗号化へ使い回さない。

現行T-Cloud／家計簿のRSA-OAEP鍵は3072 bitである。回収候補の4096 bit固定検証を改め、3072／4096 bitの復旧公開鍵を受け入れ、復旧bundle・個別記事鍵・backupのciphertext長は署名済みdirectoryの鍵サイズと一致させる。既存鍵の作り直しは行わない。公開信頼設定・vaultのJWKは公開フィールドだけを許可し、秘密鍵フィールドや未知のデータをlocalStorageやDBに保存しない。

設定保存の応答喪失時は同じ署名済み設定・全grantsとの一致を照合して再試行でき、generationや配布行を重複作成しない。新しい承認済みパスキーには、scope鍵だけでなく個別レコード鍵も既存の中央復旧鍵で再ラップする。各更新で個別レコードの完全な一覧とgrantsをサーバーでも照合し、不足・revisionの相違は保存を拒否する。鍵設定と日記更新のWorker間で完全に同時なtransactionは未実装のため、将来の移行・全件rekeyには書込停止と固定snapshotを必須とする。

credential／linkの失効、世帯・編集・ゴミ箱権限の縮小は現在のDiary accountと照合し、`rekeyRequired`で新規書込を停止する。失効を検知しただけで全件再暗号化を済ませたとは扱わない。既に渡した鍵や取得済みの内容を、API失効だけで端末から取り戻せるとは扱わない。

信頼端末で日記の復旧kitを独立したランダムAES鍵で暗号化し、そのAES鍵だけを既存のT-Cloud復旧用RSA公開鍵へラップする。サーバーに保存するのは暗号文とラップ済み鍵だけである。復旧用公開鍵のfingerprintも信頼済み端末で照合し、同じAPIから受け取った公開鍵をそのまま信用しない。既存の管理者パスワードやT-Cloud鍵の保存方式・復旧経路は変更しない。

ゴミ箱の保持対象を狭める際などに作る個別レコード鍵にも、署名済みdirectoryにある共通復旧用公開鍵へのラップを必須とする。これがないとscope鍵のkitだけでは一部の記事を復旧できない。通常閲覧ではこの復旧用ラップを使わず、共通の管理者復旧権限を持つ端末内だけで解除する。

全体のkitは全世帯を復旧できるため、復旧権限は全体管理者に限定する。統合すると共通の復旧経路を失った際の影響も共通になる。独立したオフラインキーは別経路を持つ利点があるが、保管負担が増えるため今回採用しない。既存復旧情報と承認済み予備パスキーの保管を維持する。

合成試験では、既存の共通復旧用RSA鍵を使用し、旧パスキーのPRFを使わずkitを開き、新しく承認したcredentialにgrantを発行して、既存の暗号文を復号する。復旧操作中だけ鍵の再ラップに必要なexportを許可し、通常ログインでは許可しない。更新したdirectoryに合わせて復旧envelopeも再作成できることを試験する。JavaScriptの文字列やGC対象を確実にゼロ化することは保証できない。

| リスク | 回避・緩和方法 |
| --- | --- |
| パスキーと既存の共通復旧情報を全て失う | 承認済みの予備パスキー、既存の管理者復旧情報の安全な保管、事前の実復号試験。通常の日記ログイン成功だけでは復号できない |
| 共通の復旧情報の流出 | 復旧権限を限定し、既存の本人確認・再認証・監査を維持。復旧用秘密鍵まで漏えいした場合は日記を含めてscope鍵・authorityの交換が必要 |
| 新規パスキーへの不正な鍵配布 | 既存の招待・承認に加えて、信頼端末で公開鍵fingerprintを照合し署名する。APIの承認フラグだけを信用しない |
| アカウント失効後も取得済み鍵で読める | 失効時は新epochへ再暗号化し、残る閲覧者だけに鍵を渡す。旧暗号文・既取得の平文を取り戻すことはできない |
| 古い正当なDBやdirectoryの再送 | 最低generation・端末で保持したsequence/revisionの検証。IndexedDBへciphertextと別に単調増加sequenceを保存。snapshot削除とreloadをまたぐ再送を拒否。browser storage全消去・新端末では既知checkpointが失われる制約がある |
| サーバーによる削除・隠蔽・停止 | 暗号化だけでは防げない。別系統のバックアップと、端末が署名する全件manifest/checkpointを組み合わせる |
| DB復元の誤操作 | 空の隔離DBだけへ復元し、署名とAAD関連付け、件数、実復号を検証してから切り替える |

候補の通常clientは現在epochの鍵だけを扱う。パスキー追加時にも個別レコード鍵の受取人更新と旧署名の検証情報の保持が必要であり、directoryの差し替えだけで全データを引き継げるとは扱わない。失効時はpausedで全件再暗号化し、更新済み復旧envelopeと全grantsを公開してから復元照合・再開する。移行途中の世代を通常投稿へ混在させない。本番での実端末確認は未完である。

バックアップのSHA-256は事故による破損検出であり、攻撃者に対する全体の署名ではない。各記事の署名・metadata関連付けは検証するが、攻撃者による全体の間引きや古い一式への巻き戻しには、別に保持した署名済みmanifestと最低checkpointが必要である。

## 既存データの移行と切替後の復旧

具体的な手順は上記「管理者端末と本番の残条件」を正本とする。第一管理者が承認済みの中央復旧を使い、本人の端末で全scopeを移行・更新する。通常の個人編集権限は広げない。移行用の平文dumpをGitやCodex環境へ置かず、写真本体は別工程で扱う。

移行前の旧平文へのrollbackは、新規投稿分の取扱いを決めずに実行してはならない。切替後は原則として暗号化バックアップへの復旧を使う。暗号化済みデータの問題を隠すために自動で平文へ戻す処理は設けない。

## 速度と上限

端末内索引で検索・タグ・月別移動のたびに復号・通信しない。同期はsequenceが同じなら記事転送を省き、変更時は変更されたレコードと削除・権限変更による除外IDだけを同期する。検証済みの同一暗号文を再利用する。初回は最大50件ずつ取得し、途中更新があれば全体を再取得する（最大3回）。5,000レコード・50 MBを越えた場合は停止し、分割索引を設計してから拡張する。

移行では1件ごとの全量再読込を行わない。写真IDの参照保護やrevision競合を同一transactionで処理する。大規模export/backupはD1の応答・実行上限に収まる分割と固定snapshot方式が必要であり、候補の小規模一括backupをそのまま大容量の本番cronへ接続しない。

合成試験は実端末のPRF・回線・描画性能を保証しない。本番切替の合格条件は、現在の端末で同じ操作・同じデータ量を比較し、初回解除、一覧、詳細、検索、写真一覧、長文編集の待ち時間が許容範囲にあること。普段の検索・絞り込みは操作追加遅延100 ms以内、初回の暗号処理増分はPCで1秒以内を暫定目標とし、モバイルは実測後に判断する。速度のために平文をサーバーへ戻さない。

2026-11-11の隔離Chromiumで、合成1,200件・写真metadata 21,600件を追加して測定した結果は次のとおり。PRF待ち・実際の写真画像・画面描画は計測に含まない。p95は記載した有限サンプルの観測値である。

| 測定 | 結果 |
| --- | --- |
| 初回のlocalhost HTTP＋索引処理 | 約1,174 ms（1回） |
| 暗号文検証・復号・索引処理のみ | 中央値387 ms、p95 428 ms（7回） |
| 端末内AND検索 | 中央値0.7 ms、p95 3.8 ms（21回） |
| 変更無しのHTTP同期 | 中央値4.9 ms、p95 11.9 ms（7回） |
| 写真18件のmetadataを含む1記事の編集 | 約28 ms（localhost、1回）。差分1件・約14.4 KB |

初回の暗号文索引はこのfixtureで約17 MBになる。CPU目標だけを満たしても、低速回線での快適さは保証できない。正式接続では暗号文cacheの利用と、本文用索引・写真metadataの遅延取得/分割を検討し、初回転送・画面表示の実測が合格するまで本番切替しない。現在のcandidateの全量初回取得を、そのまま現行同等と判定してはならない。

## Cloudflareの費用

このDraftの検証はローカルだけで、本番のD1/R2/Workersや他サービスの利用量を増やさない。新しい有料リソースも作成しない。

本番移行では日記だけでなく、同じアカウントの他サービスとの合算で次を確認する。契約・料金は適用時に再確認する。

| 利用枠 | 増加要因と制御 |
| --- | --- |
| D1容量 | 暗号文のbase64、署名、二重保持、変更履歴・再送receipt。本文だけでなく全写真metadataを含めて見積もる |
| D1 reads/writes | 初回索引、移行・検証、各更新のtransaction。ページ取得・変更無し応答・移行checkpointで抑制。長期の履歴/receipt清掃も必要 |
| Workers requests/CPU | ページ・鍵metadata・移行リクエスト。AES/RSAの復号は端末側で行うが、署名検証・認可・DB処理のCPUは残る。実際のWorkers CPUは今回未計測 |
| R2容量・Class A/B | 暗号化backup、新旧世代の重複、backup書込・復元読取。他サービスが既に無料枠を使っていれば増分は従量料金になる |
| その他 | logs、Queues、Cron、他サービスへのbackup転送、外部保管先。今回新たなQueueや有料originは用意しない |

例として、追加D1を100 MB以内、暗号化backupを1世代100 MB以内×42世代に制限した場合、R2 Standard $0.015/GB-monthとD1追加storage $0.75/GB-monthでは保存分の上限目安は約$0.14/月（D1が契約内なら約$0.063/月）。これは保存分だけの保守的な計算で、全体料金の保証ではない。各実行・操作課金は別である。画像本体の再アップロード・世代重複は今回の範囲に含めず、写真移行時に別途算定する。

使用量の枠を日記専用の独立枠と見なさず、他サービスの増加分も加えて月末予測する。移行バッチ量とbackup世代数に上限を設け、請求通知と実測を確認する。Cloudflareの通知は課金の強制停止機能ではない。

参考：[D1 pricing](https://developers.cloudflare.com/d1/platform/pricing/)、[D1 limits](https://developers.cloudflare.com/d1/platform/limits/)、[Time Travel](https://developers.cloudflare.com/d1/reference/time-travel/)、[Workers pricing](https://developers.cloudflare.com/workers/platform/pricing/)、[R2 pricing](https://developers.cloudflare.com/r2/pricing/)、[WebAuthn PRF](https://www.w3.org/TR/webauthn-3/#prf-extension)。
