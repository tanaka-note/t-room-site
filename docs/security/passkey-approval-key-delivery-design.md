# パスキーの招待・登録・承認とサービス鍵の引き渡し

**承認済み設計**（2026-11-22） · 調査対象 `origin/main` `e20b20ff`

## 利用者との約束

**招待 → 本人がパスキーを登録 → 管理者がSecurity Centerで承認。** この3段階で準備が完了する。承認後は、本人が許可された各サイトを直接開き、登録したパスキーでログインすれば、そのサイトで許可された機能と既存データを利用できる。本人が承認時にオンラインである必要はない。

- 日記だけを許可した利用者は、日記へ直接ログインできる。T-Cloudアカウント、T-Cloudの利用権限、T-Cloudへのログインは一切不要とする。
- T-Cloudの利用権限がある場合も、Security Centerでの承認完了時点で、許可された範囲の鍵が受け取れる状態にする。管理者が後からT-Cloudを開く操作や、利用者の「鍵の受け取りを確認」操作は通常手順から外す。
- 追加パスキーでも同じ手順を使う。各承認済みパスキーは本人に許可されたサービスに使える。アカウント、ロール、日記の閲覧範囲、T-Cloudのフォルダ範囲、Security Centerの管理権限は各サービスの現在の認可に従う。WebAuthnの秘密鍵は登録した認証器・保存サービスで管理される。

## 現行の不整合

Security Centerの現行承認は、鍵の準備状況と独立してパスキーを有効化する場合がある。T-Cloudはその後に受取側と既存管理者がT-Cloudを開くことで鍵の引き渡しを進める。このため、承認後でも暗号化データを利用できず、画面に「ログインしてください」と「ログイン済みです」が同時に出る。 [現行の承認処理](../../security-worker/src/index.js) · [T-Cloudの鍵待ち表示](../../cloud-worker/public/cloud.js) · [前回の変更 PR #282](https://github.com/tanaka-note/t-room-site/pull/282)

日記では、本人確認が通っても、既存データの鍵を配る処理が同じパスキー向けのT-Cloud管理者鍵を参照する経路がある。その鍵が未配布だと `CentralRecoveryUnavailable` で利用が止まる。家計簿にも、利用者に必要な鍵がなく、所有者の後続ログインや既存のT-Cloud鍵に依存する経路がある。これらの配布を承認処理に移す。 [日記の準備処理](../../diary-worker/public/diary-key-preparation.js) · [日記の鍵API](../../security-worker/src/diary-keys.js) · [家計簿の準備処理](../../household-worker/public/automatic-keys.mjs) · [家計簿の鍵参照](../../security-worker/src/household-automatic.js)

Edgeでスマホを求められる現象は、ブラウザとOSによるパスキーの選択に関わる。今回の調査では、Edgeのパスキー認証が成功した試行と、鍵の準備が済まずアプリを利用できない事象を確認した。登録したパスキーの保存先は特定できていない。招待画面には、PC単体で利用したい場合は保存先に「このWindowsデバイス」などのWindows Helloの選択肢が表示されたら選ぶ、と案内する。同期型パスキーは、そのパスキーのプロバイダーが利用できる環境から使う。 [Microsoftのパスキー保存先の説明](https://support.microsoft.com/ja-jp/accounts-billing/security/create-save-passkey)

## 招待から初回ログインまで

| 段階 | 操作 | システムが完了させること |
| --- | --- | --- |
| 招待 | 管理者が本人と利用サービスを確認して招待する | 現在許可されている連携と今回許可する連携を特定する。招待には対象となるアカウント・ロール・共有範囲を結び付ける。 |
| 登録 | 本人が招待画面でパスキーを登録する | 本人確認と、暗号化が有効な対象サービスの受取鍵の準備を同じ画面で行う。公開鍵と暗号化済みの受取用秘密鍵を保存し、登録と受取準備が揃った時点で「登録完了・承認待ち」と表示する。 |
| 承認 | 第一管理者がSecurity Centerで対象と権限を確認し、承認する | 直近の本人確認を行う。権限を持つ端末で必要なサービス鍵を解除し、本人の受取公開鍵向けに暗号化して保存する。すべての対象が揃ってから「承認済み・利用可能」にする。 |
| 通常ログイン | 本人が利用したいサイトでパスキーを使う | サービスのセッションと現在の権限を確認する。暗号化済みの鍵はセッション内で受け取り、本人の端末内で自動解除する。許可済みの既存データまで利用できる。 |

### 登録時の受取準備

- 端末内でサービスごとの受取鍵を作り、WebAuthn PRFを使って秘密鍵を保護する。既存のサービス別の暗号化・署名形式と用途分離を踏襲する。サービスがクライアント側の鍵を必要としない招待は、パスキーによる本人確認だけで登録できる。
- 登録時にPRF出力が得られない環境では、同じ画面で今作成したパスキーだけを指定して本人確認を行う。この場合はWindows HelloなどのOS確認がもう一度表示されることがある。対象のサービスに必要なPRF出力を使って秘密鍵を封印・解除し、登録する公開鍵と対応することを端末内で確認する。サーバーはこの登録に結び付けたチャレンジで受取鍵の所持を確認する。PRFの対応フラグだけで準備完了とは判定しない。 [W3C WebAuthn Level 3 のPRF仕様](https://www.w3.org/TR/webauthn-3/#prf-extension)
- 登録途中でタブを閉じた場合は、登録したパスキーと招待に結び付けた期限付きの準備処理から再開する。有効期限切れは管理者が同じパスキー用の準備再開リンクを発行できる。本人確認、対象credential、招待・Identity、対象の連携を照合し、チャレンジは一度だけ使用する。この認証で許可する操作は受取準備に限定する。
- 一時的なキャンセル・通信失敗は同じ画面で再試行できる。鍵を必要とするサービスでPRFを使えない場合は、承認前に対象を示して対応する環境を案内する。重複登録を誘導せず、準備済みの同一パスキーはその状態を表示する。

### 承認の成立条件

1. 承認者は現在も有効な第一管理者であり、既存ポリシーに従った直近の本人確認があること。第一管理者本人の追加パスキーは、既に承認された別の第一管理者パスキーで承認する。鍵を委譲する場合は、委譲元も対象サービスの該当アカウント・共有範囲で委譲できる権限と鍵を持つことを検証する。Security Centerの権限だけで各サービスの鍵が開く構成にはしない。
2. 承認単位ごとに、Identity、パスキー、対象連携とアカウント・ロール・共有範囲、受取公開鍵、鍵世代、失効状態を固定する。管理者端末は現在の正当な鍵を確認し、受取鍵向けに暗号化する。サーバーは同じ承認単位と世代に対応する署名・メタデータ・保存結果を照合する。受取端末も利用前に暗号文、署名や信頼情報、本人と連携・世代を検証する。
3. 全対象の鍵の保存と認可の準備が揃うまで、新規パスキーは保留にする。Security D1の単一トランザクションで承認完了、パスキーと対象連携の有効化、承認監査を確定する。別D1に保存する場合は鍵を承認ID付きで先に保存し、連携・世代を確認した保存結果を記録する。サービスは確定した承認IDに対応し、現在も有効な権限と世代の鍵だけを使う。確定後の追加の書き込みや配信を初回ログインの成立条件にしない。
4. 承認と鍵更新・失効・権限変更が競合した場合は、世代と変更番号の条件付き更新で古い準備の確定を拒否する。別D1にある変更も判定に反映されるよう、承認中の対象世代を固定できる条件をサービスごとに設け、利用時にも現在の権限と世代を照合する。日記の既存記録への鍵追加は、承認中に増えた・更新された記録も対象になるよう更新番号を照合し、差分を準備してから確定する。
5. 二重クリックや応答喪失は同じ承認IDで照会・再開する。期限が切れた本人確認は再取得する。鍵の不足や委譲元の権限不足はSecurity Centerで対象と原因を示して保留にする。すでに利用できている別のパスキーや既存の権限には影響させない。

通常時は同じ管理者が一度の承認で終えられるよう、共有範囲ごとに正当な委譲元をサービスの設定時に整備する。既存の所有者だけが鍵を持つ場合は、所有者による委譲元の準備を、その範囲の新規招待を運用開始する前に済ませる。既存の権限で委譲元を準備できない共有範囲は、その事実を管理画面に表示して招待対象への追加を保留する。鍵を紛失した場合や第一管理者の初回設定は既存の復旧・初期登録手順を使う。利用者への案内は利用対象のサービスで完結させる。

| 状態 | 表示と次の操作 |
| --- | --- |
| 受取準備が途中 | 招待画面に「パスキーを登録しました。鍵の準備を続けてください。」と表示し、同じパスキーで再開できるようにする。 |
| 承認待ち | 招待画面に「登録が完了しました。管理者の承認をお待ちください。」と表示する。 |
| 承認処理中・要対応 | 管理者に対象サービスと未完了の理由を示す。通信失敗時は同じ承認を再開する。 |
| 承認済み・利用可能 | 許可されたサービスを表示する。各サービスは通常のログイン画面から利用を開始する。 |
| 既に承認された旧登録に鍵の不足がある | 当該サイトで「本人確認が完了しました。このサービスの利用準備を管理者が確認します。」と案内する。管理者はSecurity Centerで不足を確認できる。 |

本人確認後の一時的な受信失敗は同じ有効セッションで再試行する。本人確認が完了した画面ではログイン要求の文言を外し、パスキー選択のキャンセル、承認待ち、サービス鍵の不足、通信失敗を区別する。各サイトの共通ログインカードを使い、内部エラー名は利用者画面に表示しない。

### 日記・家計簿の既存鍵からの移行

日記の現行委譲には、署名済みディレクトリを更新する権限に加え、既存の個別記録の鍵を開く手段が必要になる。日記専用の委譲元として、既存の信頼アンカーを維持した署名権限と、正当に委譲できる共有範囲の鍵・個別記録鍵を保護する。ディレクトリ全体を更新する権限を持つ鍵は、現在その権限を持つ管理者の承認済みパスキーにのみ保護して引き継ぐ。既存の委譲元で開けない個別記録鍵がある場合は、旧復旧鍵を使える管理者端末内で、対象の記録鍵に日記専用の委譲用暗号文を追加する。以後の新規・更新記録でも委譲経路を維持する。既存の暗号化データや写真の参照は引き継ぐ。 [現行の鍵設定と記録単位の配布](../../diary-worker/e2ee/setup.mjs) · [日記の暗号化の正本](diary-encryption.md)

家計簿では既存の所有者が開ける世帯鍵を元に、家計簿の所有者用・利用者用の受取鍵に対応する暗号文を作る。日記・家計簿ともに、旧T-Cloud鍵を使った復旧情報は保全する。旧復旧情報を参照する移行が必要な場合も、権限を持つ端末内での初回準備に限る。移行完了後の通常承認はサービス専用の委譲元で完結させ、T-Cloudに未登録の利用者を含む構成で検証する。 [家計簿の鍵仕様](../../household-worker/README.md) · [共通の鍵管理原則](passkeys.md)

## 既に承認されたパスキーと切り替え

1. 現在の有効なパスキー・サービス連携・鍵の準備状況を照合する。利用可能な組み合わせはそのまま使う。既存の受取鍵や受け渡し途中データは、本人・連携・公開鍵・世代が一致するものを再利用できる。
2. 不足分はSecurity Centerで対象サービスごとに補完する。受取鍵がある場合は管理者だけで補完できる。受取鍵がない旧登録に限り、本人が使いたいサイトを開き、同じパスキーで本人確認して受取準備を行う。その後に管理者が不足鍵を補完し、本人は同じサイトで利用を再開できる。権限付与済みの連携の再承認、再招待、パスキー削除、T-Cloudへの迂回は不要とする。
3. 追加型の保存形式と読み取り互換性を先に用意する。旧データと新しい委譲用暗号文、承認の確定状態、失効状態を復元できるようBackup Workerの許可リストとスキーマを合わせる。実際のバックアップから隔離環境へ復元し、端末内で全件・鍵世代・既存鍵の利用を照合してから有効化する。
4. 対象サービスの確認と公開を揃えて新方式を有効にする。切り戻し時は新方式の承認開始を停止し、確定済みの鍵・承認状態・失効は維持する。第一管理者パスワードは既存の復旧経路に使う。 [公開手順](../development-flow.md) · [パスワードと復旧の正本](password-auth-policy.md)

PRF出力、復号鍵、秘密鍵、平文データは端末内で扱う。Cloudflare・GitHub・監査ログにこれらを渡さない。監査には承認の開始・確定・失敗、鍵の補完、失効、本人確認の結果を秘密情報を含めずに記録する。失効時はセッションと新規の鍵取得を停止する。既に端末で取得した鍵への対応は、現行と同じく必要な範囲の鍵世代更新で行う。

| T-Cloud管理者・フォルダ利用者 | 先行するT-Cloudログインや鍵確認ボタンを使わず初回ログインできる。管理者本人には既存ファイル、フォルダ利用者には割り当て範囲のファイルだけが開く。 |
| 世帯・台帳・管理権限 | 家計簿の別世帯、請求書の別台帳、日記の非公開範囲、Security Centerの管理権限にアクセスできない。各サービスで許可された読み書きができる。 |

| 中断・競合・失効 | 登録画面を閉じても同じパスキーで続行できる。鍵保存の一部失敗、承認応答の喪失、二重操作、鍵更新・権限変更・失効の競合を再現し、早すぎる有効化、二重適用、古い鍵の引き渡しが起きない。 |
| 過去の承認・復旧 | 承認済みで鍵が不足する登録を、同じパスキーで補完できる。隔離環境にバックアップを実際に復元し、既存データと新方式の鍵の利用、失効済みの鍵の拒否、第一管理者の復旧を確認する。 |

## 実装と切り替えの確認

日記の初回移行では、既存の復旧鍵を開ける管理者端末で、日記専用の委譲鍵を生成する。過去の個別記録鍵は暗号化した委譲用の鍵セットに追加し、元の記録や写真は再暗号化しない。以降の個別記録鍵は、既存の復旧用公開鍵と日記専用の委譲用公開鍵の両方に包む。通常承認では、管理者自身の日記の受取鍵から委譲用の鍵セットを開く。新旧の個別記録鍵、現在の署名済みディレクトリ、承認者の役割を照合する。最終照合中だけ日記の記録更新を保留し、既存セッションの世代は維持する。

公開はBackup Worker、鍵配布を受け付けるDiary・家計簿・請求書のWorker、Security Centerの順で整合を確認してから進める。既存のSecurity D1に `0034_tcloud_admin_key_transfers.sql` の適用が必要。切り替え前に隔離環境への復元で、旧記録、委譲鍵の世代、T-Cloud受取前の暗号文、失効状態を照合する。Windows Helloと同期型プロバイダーは実機の確認結果を切り替え記録に残す。
