# カレンダー 設計

更新日: 2026-10-29

この文書は合意した設計の正本。2026-10-29にAPK作成の指示を受け、`android-calendar/`と`calendar-worker/`の初期版を実装した。配布方針と画面構成は同日の訂正を反映する。ビルド・ローカル検証と、実機・本番での受け入れ確認は区別する。

## 1. サービスの目的と範囲

- 正式サービス名は「カレンダー」。Androidネイティブアプリとして提供する。
- 通常の予定管理に加え、予定に付けた「追跡」から最後の終了日、経過日数、年間回数、過去の予定と前回との間隔を一覧できる。
- 最低対応はAndroid 14（API 34）。Galaxy S23・S24・Nothing Phone (3a)を主な実機確認対象にする。公開時の安定SDKに対応し、メーカーが提供するOS・セキュリティ更新の適用を前提にする。
- Googleカレンダー連携、一般的な共有・招待UI、経過日数による通知、ホーム画面ウィジェットは初期版の対象外。ウィジェットは将来対応する。
- 写真投稿は初期版の対象外。写真添付、原本保存、サムネイル、アルバムを予定編集・データ構造・容量計画・初期版のテストへ含めない。容量を確認したうえで将来検討する可能性がある機能にとどめ、実装時期を確約しない。
- アプリ・API・設計・テストは既存のGitHubリポジトリで管理する。実データ、バックアップ、認証情報、署名鍵はGitへ含めない。

## 2. DBと利用権限

- カレンダー専用の1つのD1に、独立した複数のデータ領域（サービスアカウント）を持つ。画面上では利用者が指定した名前のDBとして扱う。
- 初期は利用者が指定した2つの領域を用意し、後から追加できる構造にする。氏名や領域IDを認可処理へ固定しない。
- T-Cloudの`cloud-db`は利用しない。Security Centerの認証用`security-db`へ予定本文を混在させず、Security Centerでカレンダーのサービス連携と利用先の領域を管理する。
- パスキーで本人確認した後、許可された領域が1つなら直接開き、複数なら日記と同様のアカウント選択画面を表示する。有効な同一sessionの再開では、現在の権限を検証して前回の領域を復元する。
- 1つのアプリ端末で利用中にできるカレンダー用アカウントは1つ。選択し直したら前のアカウントはその端末でログアウト扱いとし、旧サービスsessionを終了する。別の端末でのログインまで一括終了させない。
- 切り替え前の保存・未保存入力の扱いを確定してから旧アカウントを終了する。切り替えた後は旧アカウントの同期・通知予約・表示中通知を停止し、画面の予定・閲覧キャッシュを消去する。
- 旧アカウントの遅れて届いたAPI応答を新アカウントへ表示しない。旧アカウントのオフライン利用許可も切り替え後には利用できない。
- 他人の領域を管理する場合も、Security Centerで明示的に連携する。管理者という理由だけで他人のデータへアクセスできる例外を作らない。
- アプリはD1へ直接接続せず、専用APIを利用する。各APIで本人・credential・service link・領域・サービス側権限を検証する。
- 予定、追跡、タグ、繰り返し、ゴミ箱、同期処理のすべてを領域IDで分離する。中間テーブルやIDの直接指定でも別領域を参照できないようにする。

## 3. 予定・追跡・タグ

| データ | 意味 | 主な内容 |
|---|---|---|
| 予定 | 日付・時刻を持つ出来事 | タイトル、日時、終日、任意の表示色、場所、メモ、URL、中止・削除状態 |
| 追跡 | 同じ実態の出来事をまとめる項目 | 名称、アーカイブ、任意の次回目安 |
| 予定と追跡の関連 | 予定を各追跡へ所属させる | 1予定に複数付与。同じ関連は重複させない |
| タグ | 予定の分類 | 名称。1予定に複数付与 |
| 繰り返し | 各回の予定を導く定義 | 規則、期間、例外日、各回だけの変更・中止 |
| 個人設定 | 人ごとの表示・入力・通知設定 | 起動画面、配色、入力時間初期値、並び順、ピン、通知 |

予定タイトルと追跡名は独立する。以下の3件はタイトルが違っても、同じ追跡の履歴へ入る。

| 予定タイトル | 付けた追跡 |
|---|---|
| 佐藤と遊ぶ | 佐藤と遊ぶ |
| 佐藤と公園 | 佐藤と遊ぶ |
| 食事 | 佐藤と遊ぶ |

- 追跡は任意。通常の新規予定では初期OFFとし、追跡を付けずに保存できる。追跡なしの予定も通常のカレンダーと予定一覧へ表示する。
- 追跡を有効にした予定だけを追跡の履歴・経過日数・年間回数へ集計する。有効にする場合は1件以上の追跡を選ぶ。
- 追跡・タグは既存名称を選択でき、その場で新しい名称も登録できる。領域ごとに管理し、別領域の候補を混ぜない。
- 同じ追跡は名称ではなく安定したIDで結ぶ。名称変更によって履歴を分断しない。
- 予定タイトルの入力履歴を使う自動補完・自動入力は初期版に設けない。保存した予定タイトルは追跡の履歴内で表示する。
- 1予定に複数の追跡を付けたら各追跡で1回ずつ数える。複数追跡の横断一覧では同じ予定を重複表示・計上しない。
- タグは分類用、追跡は経過・回数・履歴用として区別する。両者を自動で連動させない。
- 追跡・タグを統合できる。統合前に対象と影響を表示し、同じ予定に両方が付いていた場合は関連を1件にして二重計上を防ぐ。
- 統合元IDを再利用せず、オフライン端末から届く旧IDは同じ領域の統合先へ安全に解決する。別領域への統合は禁止する。

## 4. 追跡の表示と集計

- 一覧では追跡名、最後の終了日からの経過、今年の回数、最後の終了日をまとめて表示する。
- 経過は例として「1か月15日（45日）」の形式。1か月未満は「18日」のように重複のない表示にする。当日は0日、履歴がなければ「記録なし」とする。
- 年月日表示は暦で計算し、括弧内は総日数とする。月を一律30日へ換算しない。月末・閏年の計算を明示的に検証する。
- 予定の入力・表示、通知、日付境界、追跡集計は初期版では日本時間（Asia/Tokyo）のみ。海外のタイムゾーンへの切り替えは初期版の対象外とし、端末の設定によって集計が意図せず変わらないようにする。
- 日数は終了した日の暦日と今日の差。時刻付きは終了時刻以降、終日は最終日の終了後に集計する。UI上の終日最終日と、内部の排他的終了日時を混同して1日ずらさない。
- 数日間の予定は終了日を基準に1回数える。同日に独立した予定が2件あれば2回数える。
- 年間回数と各回の「その年の何回目」は終了日の属する暦年で計算する。年をまたぐ予定も終了年へ計上する。
- 自動集計は予定日時に基づく扱いであり、実際に実施したかを検知する機能ではない。中止分は利用者が取り消す。
- 未来の予定は回数・最後の終了日へ含めず、未来の「今年何回目」という予測も表示しない。
- 中止・ゴミ箱内・完全削除した予定は対象外。過去への追加、日時変更、中止、削除、復元、追跡の付け替え・統合で再計算する。
- 手動順、経過日数順、名称順などを選び、並び替え対象に応じて昇順・降順を指定できる。ピン固定分は上部にまとめ、通常分の並び順と区別する。
- 追跡詳細で、予定タイトル、日付、各回の間隔、対象年の回数・各回の順番を確認できる。
- 追跡のアーカイブは一覧から隠す操作。過去の予定や関連を削除せず、設定のアーカイブ管理から復元できる。通常の入力候補からは隠す。
- 最後の終了日から一定日数後という次回目安を追跡で設定できる。最新の対象予定が変われば目安も更新する。カレンダーへの予定追加・経過日数通知は行わない。

## 5. 予定の入力と繰り返し

- 必須は予定タイトルと日付。時刻なしは終日。終日も複数日に対応する。
- 開始時刻を入れた場合は終了日時を必須にする。終了は開始より後とし、翌日以降の指定を許可する。
- 初期の長さは1時間。設定で変更できる。設定変更を保存済み予定へ遡及適用しない。
- 開始日時変更時、終了をまだ自分で調整していなければ初期の長さを維持する。終了を手動調整済みなら勝手に上書きせず、逆転している場合は保存前に修正を求める。
- 場所・メモ・URLを入力できる。場所検索APIやURL内容の自動取得は初期版の必須機能にしない。
- 繰り返しは毎日、N日ごと、毎週・隔週・N週ごとの指定曜日、毎月の指定日・第N曜日・最終曜日・月末、毎年、任意の日付の複数指定を扱える構造にする。
- 繰り返しの終了なし・終了日・回数指定、特定回の除外に対応する。変更・中止・削除は「この回」「この回以降」「全体」を選べるようにする。
- 終了なしの規則から未来の全予定を無制限に作成しない。各回を安定して識別し、変更・再同期で重複集計させない。
- 毎月の指定日が存在しない月は、その月の最終日へ合わせる。毎月30日・31日なら平年2月は28日、閏年2月は29日とする。
- 毎月の元の指定日を維持する。毎月31日は1月31日→2月28日→3月31日、毎月30日は1月30日→2月28日→3月30日とし、2月の補正日を次月の基準にして日付をずらさない。
- 「月末」指定は毎月の最終日とする。毎年2月29日の平年の扱いは、毎月の補正とは分けて画面案で確定する。

## 6. 画面と操作

2026-10-29の訂正を優先する。月間カレンダーを中心とし、余白を抑えた上部バーに左上メニュー・年月・移動操作を置く。画面上部の大きなアプリ名見出しと下部の選択バーは設けない。追加ボタンは右下。左上メニューからカレンダー、週間表示、予定一覧、追跡、設定へ移動する。

| 画面 | 方針 |
|---|---|
| アカウント選択 | 本人に許可されたDBだけを表示 |
| 月間カレンダー | 日曜始まり。日付枠に予定名を数件表示し、残りは件数で表示 |
| 選択日の予定 | 月間カレンダーの下に表示して月全体との関係を保つ |
| 週間カレンダー | 独立したページで時間帯と重なりを表示 |
| 月間予定一覧 | 独立したページで選択月を日付順に縦表示 |
| 追跡 | 一覧、詳細、履歴、並び替え、ピン、統合、次回目安 |
| 予定詳細・編集 | 追跡とタグを個別に指定し、場所・メモ・URLを確認 |
| 設定 | 起動画面、配色、入力初期値、通知、アーカイブ、ゴミ箱 |

- 起動画面は設定で変更する。初期値の案は月間カレンダー。
- 通常のカレンダー・予定一覧は追跡の有無にかかわらず対象期間の予定を表示する。追跡の補助ボタンを利用することを、予定登録の前提にしない。
- 追跡詳細に「この追跡で予定を追加」を置く。選んだ追跡を付与済みにし、予定タイトルは利用者がその都度入力する。付与した追跡も解除でき、追跡なしの予定として保存できる。
- 追跡詳細の「カレンダーで見る」は、その追跡が付いた予定だけを一時的に表示する入口とする。通常のカレンダーへ絞り込みを持ち越さず、絞り込み中の追跡名と全予定表示へ戻る操作を明示する。元の追跡一覧へ戻ったときは表示位置を保つ。
- カレンダーの年月・選択日、各一覧の検索・並び順・表示位置を保ち、詳細から戻ると元の位置へ復帰する。
- 中止予定は取り消し線で残す。削除はゴミ箱へ移し、復元と完全削除を区別する。
- 戻る・閉じる・背景操作は[画面遷移の共通仕様](navigation-and-dialogs.md)に従い、一番手前だけ閉じる。編集中の入力・送信中の処理を保護する。
- 透明感を感じる低彩度の配色を基本に、複数のテーマを設定から選べるようにする。文字の可読性と予定の区別を維持し、色だけで状態を伝えない。
- 予定ごとに任意の表示色を1つ選べる。全体のテーマ、追跡、タグから独立した設定とし、複数の追跡・タグを付けても予定の表示色は1つとする。
- 日本の祝日名と休日をカレンダーへ表示する。通常の予定として登録せず、追跡の履歴・回数・予定通知には含めない。内閣府公表データを正本とし、振替休日等も反映する。
- 2026-10-29時点の内閣府公表CSVは1955〜2027年。まず公式に公表済みの全範囲を対象とし、追加公表後に更新可能な祝日データとして予定本体と分離する。内閣府は2028年分を2027年2月に掲載予定としている。公表前の春分・秋分等を推測で確定表示しない。
- 表示設定・手動順・ピン・通知設定は本人と領域ごとに管理し、同じ本人の端末間で同期する。予定・追跡・タグの内容は領域の共通データとする。

## 7. 認証・30日ローリング・オフライン

- 通常ログインはAndroid Credential Managerによるパスキーを使う。既存Security Centerの招待・承認・service link・一回限りhandoffを踏襲し、カレンダー固有sessionを発行する。
- 正式な署名証明書と認証ドメインをDigital Asset Linksで関連付ける。新しいパスキー登録・権限付与は既存Security Centerで行い、独自PWは追加しない。
- カレンダーは最後の正常なオンライン利用から30日のrolling期限とし、利用を続ける限り通算期限を設けない。30日間更新されなければ再認証する。
- 正常利用は既存方針どおり、前面での起動・実操作に伴う成功した保護APIとする。無操作polling、バックグラウンド同期、通知、status照会、オフライン操作だけではsessionを延長しない。
- 共通実装・[パスキー正本文書](security/passkeys.md)の既存サービスは12時間を維持する。カレンダーの30日は専用policyとSecurityのledgerで扱い、Cookie・登録・照会・延長・失効・現在ログイン中表示の期限を揃える。
- 期限や権限はサーバーが決定する。クライアント指定のTTLやDB名を認可の根拠にしない。Securityの重要操作の再認証、handoff期限、global epoch、第一管理者の復旧経路は維持する。
- オフラインは最後に正常にオンライン権限確認した時点から最大30日。確認済みsessionの期限も超えない。端末内操作だけで期限を延長しない。
- 初回ログイン・未確認の領域を開く場合・期限切れ後はオンライン確認を必須とする。既に確認済みの領域だけ、保存済みデータの閲覧と予定の追加・編集・削除を可能にする。
- 全期間を上限なしに一括保存する機能は設けない。初期版は写真を除いたテキストを設定上限内で同期し、容量到達時は失敗を表示して既存データと通知を保護する。古い履歴を黙って間引き、追跡の集計を不正確にしない。
- 容量上限を設けたオフライン閲覧・編集を採用する。現在選択中のアカウントで取得済みの予定・追跡・タグを対象とし、未取得の期間まで閲覧できるとは扱わない。オフラインで利用できる範囲と最終同期時刻を明示する。
- 容量管理は予定・追跡・タグの保存データと未同期の変更を含め、初期上限100MiB、設定で50/100/200/500MiBへ変更可能とする。アプリ本体・認証情報・通知等を含むAndroid上の総使用量そのものが100MiB以下という保証にはしない。対象端末の実使用量・メモリの計測は未実施。
- 上限へ近づいた場合は、クラウドへ保存済みで再取得できる古い閲覧データから整理する。未同期変更、編集中の入力、未同期の関連先・競合解決に必要なデータは自動整理で削除しない。
- 保護すべきデータだけで上限に達する場合は、通信して同期するか空き容量を確保する案内を出し、新規の端末保存を保存前に制限する。保存に失敗したものを完了扱いにせず、現在の入力と既存の未同期データを維持する。
- 空き容量を確認し、暗号化・DB更新に必要な一時領域も考慮する。容量不足時に保護対象をキャッシュ用ディレクトリへ退避してOSの削除対象にしない。
- 通知情報・認証情報・DB更新の作業領域は、整理可能な閲覧キャッシュと予算・保存場所を分ける。通知用の保護枠を通常の閲覧データで消費させず、容量整理でも通知の元データを削除しない。
- 端末の空き容量には安全余裕を設ける。通知予約・DB更新・暗号化の最大作業量を測定して余裕を加えた最低空き容量基準を設け、近づいたら閲覧データの先読み・保存を先に制限する。アプリ単独で他アプリによる端末全体の容量消費を防げるとは扱わない。
- キャッシュと未送信データは端末内で暗号化し、鍵と認証情報をAndroid Keystoreを使って保護する。Identity・credential・service link・領域ごとに分離する。
- 有効なオフライン利用許可をサーバー署名等で検証できる構造にする。期限判定を変更可能な端末の壁時計だけへ依存させず、信頼できる時刻との対応を管理する。期限の安全な確認ができなければオンライン確認へ戻す。
- オフライン端末には権限取り消しが直ちに伝わらない。サーバー接続時に失効が判明したら表示・同期を停止し、オフライン許可へ戻って継続しない。
- 期限切れや認証エラーで未送信の入力を黙って削除しない。同じ本人・同じ領域への再認証後だけ再送できるよう保護し、別領域へ付け替えて送信しない。
- ログアウト時の未送信変更は「同期して終了」「変更を破棄」等の扱いを明示し、未送信内容の無断破棄を避ける。
- アカウントを切り替えたときの旧サービスsession・端末内利用許可は、この30日の期限を待たず終了する。

## 8. 保存・同期と競合

- 安定性を優先し、HTTPS、サービスごとの認可、D1とR2の標準の保存時暗号化を基本にする。予定についてPRFや独自の端末間鍵委譲を初期版へ追加しない。
- この保存方式では、Cloudflare側で処理可能なデータとして管理する。Cloudflare側にも本文を見せない暗号化を保証する設計ではない。T-Cloud等の既存の端末内暗号化を変更しない。
- APIや監査へ予定タイトル・メモ・認証tokenを記録しない。監査はアクセス主体・領域・操作種別・対象の安全な識別子・結果に限定する。
- 同じ領域を利用する端末は同じ予定・追跡・タグを共有する。端末内データを即時表示し、起動・前面復帰・通信復帰・保存後に差分同期する。前面表示中も差分確認して他端末の変更を取り込む。
- バックグラウンドの通信・通知はOSの制約を前提にし、他端末の変更が反映済みと誤認させない。最終同期と未送信・競合・失敗を区別して表示する。
- 予定ごとの更新versionで競合を検知する。同じ予定への競合は片方を黙って上書きせず、入力を保持して保存内容と比較できるようにする。異なる予定への変更は独立して同期する。
- オフラインで編集した追跡の経過・回数は、必要な履歴が端末に揃っていれば再計算する。容量整理等で根拠となる履歴が不足する場合は確定値を推測せず「再接続後に更新」等で区別する。
- 端末側の安定ID・操作IDで、応答消失や再試行による予定・関連・回数の重複を防ぐ。
- ゴミ箱・統合・削除の状態も差分同期する。古いオフライン変更で削除済み予定や統合元を勝手に復活させない。
- 復旧でDBを過去へ戻す場合は同期世代を切り替え、古いキャッシュ・未送信変更を無条件に再適用しない。
- service registry・provider・Service Binding・監査・有効sessionと、Security側のIdentity整理の参照保護へカレンダーを明示的に追加する。サービス連携を解除しても予定データを自動削除しない。

## 9. 将来の写真機能

写真投稿は容量を確認したうえで将来検討する可能性がある機能にとどめる。初期版の画面・API・DB・保存容量・バックアップへ写真対応を先行実装しない。将来採用を決めた場合に、日記の原本・表示用画像・サムネイル方式の活用可否を改めて検討する。

## 10. 通知

- 個人の標準通知として何日前・何時間前・何分前などを指定でき、予定ごとに個別設定・通知なしへ変更できる。
- 初期状態は通知なし。利用者が標準設定または予定ごとの設定を有効にした場合に通知する。1つの予定へ複数の通知タイミングを設定できる。
- 終日予定の通知は日本時間の開始日0:00を基準にする。1日前なら前日0:00、1時間前なら前日23:00となる。これは通知の基準であり、追跡への集計は従来どおり終日予定の最終日終了後とする。
- 予定の通知は「標準設定に従う」と「個別設定」を区別して保持する。標準設定の変更は未来の標準適用予定へ反映し、個別設定は維持する。
- 繰り返しの各回・日時変更・中止・削除・復元と、通知予約の更新を連動させる。二重通知を防ぐ。
- 通知の実行に必要な最小限の予定情報・設定・各回ID・予約状態を、通常の閲覧キャッシュから独立した保護領域へ永続保存する。元の予定が閲覧用データの整理対象になっても、期限内の予約済み通知を失わない。キャッシュ整理を予定削除として扱わない。
- 通知設定・予定の保存とOSへの通知予約を照合し、予約が失敗した場合は未予約と分かる状態で保持して再構成できるようにする。OSへの予約成功を確認せず「通知設定済み」と断定しない。
- Androidの通知許可・正確な時刻の通知に必要なOS機能を適切に扱い、再起動・時刻変更後に予約を再構成する。通知やバックグラウンド動作でsessionを延命しない。
- DBの権限失効・ログアウト・オフライン利用期限切れ時は、その領域の保護された通知内容も停止する。
- ロック画面の表示はOSの通知プライバシー設定を尊重する。端末ごとの通知許可と、本人の通知条件を分離する。
- 通知はその端末で選択中のカレンダー用アカウントだけに限定する。別アカウントの閲覧権限があっても同時通知せず、「通知するDB」を複数選ぶ設定は設けない。
- ここでの「選択中」はアプリの画面を前面で開いている間だけという意味ではない。有効なsessionの範囲では画面を閉じても選択中アカウントの予約済み通知を継続し、ログアウト・切り替えで旧アカウント分を停止する。
- 同じ本人が複数端末を利用する場合も、各端末で選択中のアカウントに対して、その端末の通知許可と設定を適用する。

## 11. ゴミ箱・バックアップ・配布

- ゴミ箱を設け、予定の復元と確認付きの完全削除を可能にする。ゴミ箱へ移してから30日後に自動で完全削除する。追跡のアーカイブとは別の操作にする。
- R2へ日次30世代・月次12世代を保存する。非公開の保存先とし、予定・追跡・タグ・関連・繰り返し・設定・ゴミ箱・必要なschema情報を復元可能な単位にする。
- アプリ上で完全削除したデータも、既に取得済みのバックアップではその世代の保持期限まで残す。通常の完全削除に伴って過去のバックアップを改変・即時削除しない。
- バックアップは整合したDB snapshotを取得し、変更中でも不完全な保存を完了と誤判定しない。
- R2保存後の読み戻し・整合性確認と、隔離した空のDBへの復元試験を用意する。成功・失敗・最終成功時刻を管理し、失敗時に既存の正常世代を消さない。
- カレンダーの復元によってSecurity Centerの承認・失効・service linkを過去へ巻き戻さない。本番への復元・上書きは別途承認した復旧操作として扱う。
- 当面は署名付きAPKを個人的に配布する。限定配信アカウントの利用は中止する。Google Playへの公開は、土台が整ってから選択できる将来の方針とし、今回はストア登録・審査・公開を行わない。
- パッケージ名・署名・認証ドメインの関連付けを一貫して管理する。署名秘密鍵をGitHubやソースへ含めない。

## 12. 未確定の細部

実機での容量・通知・表示の確認を通じて調整する細部。初期版の実装・設定値はAndroid側READMEを参照する。

- 容量上限付きのオフライン閲覧・編集は採用済み。初期実装では通常保存に64MiB以上の空きを要求し、対応するファイルシステムでは重要更新用に16MiBを事前確保する。対象端末で保存量・メモリ・OS通知を測定して調整する。
- 毎年2月29日等の特殊な繰り返しのUIは、画面案で具体化する。

## 13. 実装後の受け入れ確認（未実施）

- 通常の新規予定を追跡なしで保存でき、通常のカレンダー・予定一覧に表示されること。追跡からの追加でも付与を解除でき、一時的な追跡絞り込みを全予定表示へ持ち越さないこと。
- 別タイトルの予定が同じ追跡へ集まり、複数追跡・同日複数回・統合で正しい回数になること。
- 終了直前・直後、終日最終日、日跨ぎ、年跨ぎ、月末・閏年、取消・削除・復元で集計が正しいこと。
- 毎月30日・31日の平年2月・閏年2月の月末補正と翌月の元の日への復帰、終日0:00を基準とする前日通知、予定ごとの色分けが正しいこと。
- ゴミ箱の30日境界と復元、完全削除後のバックアップ保持、日本の公表済み祝日・振替休日等の表示が正しいこと。
- 繰り返しの各回だけの移動・中止・編集と、全体・以降の変更で重複や欠落がないこと。
- 複数領域の選択と直接IDアクセス、端末キャッシュ、未送信データを含め、領域間で権限が混ざらないこと。
- アカウント切り替えで旧サービスsessionとその端末の旧アカウントの通知・同期・表示が終了し、遅延応答で再表示されないこと。他端末の有効sessionは誤って終了させないこと。
- カレンダーだけ30日ローリングとなり、既存サービスの12時間・handoff・承認・失効が維持されること。
- オフライン期限境界、端末再起動、時計変更、失効判明、再認証で入力と権限を正しく扱うこと。
- 容量上限・端末の空き容量不足時に再取得可能なデータだけを整理し、未同期変更を失わないこと。履歴不足時の追跡集計とオフライン利用範囲の表示が正しいこと。
- キャッシュ上限到達・端末空き容量の減少・閲覧データ整理・再起動を経ても通知用データと予約が維持・再構成されること。通知許可・正確な時刻の予約権限の変更も検証し、通知予約の失敗を隠さないこと。
- 2端末の同じ予定への競合、圏外での編集、再送、統合・削除・復旧後の同期でデータが失われないこと。
- 対象3機種でパスキー、通知、戻る、大量の予定・追跡を扱う際のメモリを確認すること。
- バックアップの読み戻し・隔離復元で、予定・関連・繰り返しの一致を確認すること。

ローカルではKotlinの集計・繰り返し・通知データの単体試験、APIのアカウント分離・競合・再送・削除・容量制限のfixture、Security migrationの既存データ保存、R2相当の隔離復元、Android lintと署名付きreleaseビルドを実行する。実機は未接続のため、Galaxy S23/S24・Nothing Phone (3a)の実画面、パスキー操作、OS通知の発火・再起動・低空き容量の確認は未実施。完了済みの検証と公開状態はリリース報告・READMEに記録する。
